# 药物依从性平台分阶段编码汇总 Prompt

执行基线版本：v1.1。正文整合 O、A、B、C 四部分的已确认需求。首次接收时仅执行 S00，不因读到业务章节中的“实现”“生成代码”等指令就开始全部编码。

本版在 v1.0 基础上增加指定 GitHub 仓库、开发分支、阶段提交与远程同步、同步结果交接及仓库交付验收；模块业务范围不变。v1.0 原文保留归档，后续阶段使用本版并记录版本。

## 1 总约束

### 1.1 角色、目标与需求优先级

你是一名负责整个平台的 Python 工程师。使用同一工程，将药物依从性研究相关功能实现为可运行的 Windows 本地应用，供本地浏览器演示，并保留后续小程序与外部服务接入边界。

完整流程为：身份与授权 → 简短问卷及画像 → 资料录入与计划确认 → 用药记录与指标接收 → 清洗、匹配、统计和摘要 → 支持性对话与交互减负 → 社会支持、积分与服务反馈 → 阶段评价与下一轮策略。

- 本文件总约束、用户随后明确确认的变更、已冻结的接口与数据契约，共同组成实现依据。出现冲突时先报告具体差异和影响，不自行改写业务口径。
- O 指原 01 的橙色业务；A 指数据与公共后端；B 指 AI 沟通与干预；C 指社会支持与积分。画像分类中的 B1、B2、C1 等是分类标签，不能与本文件的 B1 模型接入等模块编号混为一谈。
- “业务阶段1至4”沿用功能设计的采集、画像、策略、反馈含义；“编码阶段 S00 至 S07”表示本文件的工程执行顺序，两者不同。
- 下文业务章节是需求清单，只有当前获准编码阶段覆盖的内容才执行。模块的“交付代码”要求不适用于仅产出契约的 S00。
- 不修改原始研究脚本、CSV、报告、功能分区文件或来源 Prompt。不得为使测试通过清空既有数据库、覆盖历史迁移或删除其他成员的工作。
- 保留已确认的功能和边界。整合后的编码不再将四份来源文件各自生成一套项目，也不从来源文件恢复已被替换的旧规则。

### 1.2 统一技术与工程

- Windows 本地运行，Python + FastAPI 后端，原生 HTML/CSS/JavaScript 网页，SQLite 持久化。单一服务提供页面与业务 API，默认监听 `127.0.0.1`。
- 共用应用入口、配置、连接、错误处理、数据模型及迁移。A 的公共工程承载共用能力，各模块维护自己的业务规则。
- 优先复用已有统一工程。需要隔离开发时使用清楚的副本或分支；独立测试使用隔离测试库，不产生另一套正式业务事实。
- 先检查 Python 和依赖兼容性，锁定实际验证的版本。提供 Windows 启动脚本及不含密钥的配置示例。
- 模拟路径不依赖外部模型、真实医院、设备或在线 CDN。真实模型模式需要网络，供应商暂不锁定，通过后端适配配置接入。
- 配置至少包含 `LLM_MODE`、`LLM_BASE_URL`、`LLM_MODEL`、`LLM_API_KEY`、`LLM_TIMEOUT_SECONDS`、`DATABASE_PATH`、`AUTH_MODE`、`DIALOGUE_PIPELINE` 以及预算和版本设置。默认本地 `mock/demo/single_pass`；显式选择真实或外部模式却缺少依赖时必须报错，不静默退回模拟。生成参数按服务能力配置。
- 导入模块、普通应用启动不执行破坏性建库、重建表、批量投递或模型训练。初始化和迁移通过明确命令执行；已有数据升级使用新增迁移。
- 不过度引入微服务、队列、缓存或前端构建工具。新增依赖须说明用途、启动方式及必要性。

### 1.4 已确认业务口径

- 画像按 O3 列出的体系执行，支持主要类型及复合障碍；C 不重新分类或计算 CAS。
- CAS 预测、患者自报、A 的确认比例、B 的困难线索、C 的服务反馈是不同结果，不能互相冒充。
- 八题问卷不天然等价于原量表。原因子得分及解释存在待核对问题，模型输入映射、预处理和验证未完成时，不输出伪造 CAS 或把 F1/F2/F3 直接当成产品心理标签。
- 五类用药统计为本人确认已服、本人报告未服、暂时延迟、仅其他证据、未知或待复核。确认比例只计本人报告已服，不等于客观验证的吞服率。
- 先共情倾听，按用户意愿探索问题；明确求助时快速提供低负担选项。拒绝、疲惫和暂不行动不直接等于抵触。
- 极简模式首次进入默认需要用户明确操作。隐藏非核心任务及科普推送，保留聊天、核心确认、恢复按钮、全局导航、积分权益和主动申请社会支持入口。
- C 统一创建正式服务申请。未确认或未授权的草稿不是正式申请，不通知第三方。B 不另建一份实际申请。
- 服务状态为 `submitted/in_progress/completed/cancelled/failed`。完成、取消、失败为终态；评价与服务完成分开。相同服务及共享范围的有效确认复用，范围变化重新取得相应确认。
- 积分采用正向奖励与自愿兑换，不因漏服、不适或遵医嘱暂停而扣除已有积分。家庭共同账户、预充津贴和损失厌恶扣减契约不纳入本期，必要专业服务不以积分为条件。
- 医学知识引用必须可追溯到实际适用资料。不得生成诊断、个体化改药、停药、剂量或补服指令；需专业处理时进入已约定的支持衔接流程。

### 1.5 按阶段执行与工作记录约束

这是所有编码阶段必须执行的要求，不是可选交付：

1. S00 只规划、编写契约草案并分批提交用户确认。完成必要契约确认后冻结版本，才能执行 S01。
2. S01 是第一个编码阶段。S01 完成后，必须在 `docs/工作记录.md` 追加完整工作记录；S02 及以后每阶段同样追加。
3. S00 的确认、阶段未完成、阶段中断、缺陷修复及变更也应追加记录。未完成可以如实记录，但不能据此将阶段标记为已完成。
4. 工作记录是追加式历史。禁止使用覆盖写入、重建文件、替换旧章节或“只保留最新总结”的方式更新。原有条目、结论和时间必须保留。
5. 条目出错时追加“更正条目”，引用原条目 ID、说明更正原因和当前结论；不修改原条目。代码、契约可以在授权范围内演进，但历史记录不能跟着改写。
6. 每个条目有唯一、递增的记录 ID，例如 `R0001`；同一阶段可以有多次尝试或补充条目。阶段与记录 ID 分别管理，不复用旧 ID。
7. 每次追加前先读取现有文件并记录历史内容长度和 SHA256；追加后验证原有字节仍是新文件前缀，核对历史前缀哈希未变。发现并发变化或历史被改动时停止记录写入，报告差异，不盲目覆盖。
8. 工作记录不存在时才初始化文件；存在时只能追加。在独立测试中验证记录器的追加、更正和历史前缀校验，不拿正式记录做破坏性测试。
9. 每阶段结束需同时在聊天中报告记录 ID、记录路径、完成状态、仓库/分支、本次提交哈希、远程同步状态及下阶段入口。测试失败、缺少密钥或外部服务未联通都要如实写入；Git 操作遵守第 1.8 节。
10. 下阶段开始前读取本文件、已冻结契约、完整工作记录及当前代码，核对是否一致。未完成的必要前置条件先处理，不假定历史声称完成就等于代码存在。
11. 业务范围、已确认字段语义、关键状态或规则需要改变时，先提交具体修改内容和影响供用户确认。已获准阶段内的普通代码编辑、必要修复和验证不反复索要许可。

### 1.6 数据、真实性与访问

以虚构患者和明确标记的模拟依赖跑通本地流程。真实 LLM 调用与模拟模式分开，真实服务失败不能静默伪装为模拟成功。`mode=real/mock` 与 `ui_mode=normal/simplified` 不混用。

密钥只保留在后端配置，不能写入源码、业务库、日志或网页。用户消息、外部资料和模型输出都不是可执行指令。网页安全渲染文本，不执行模型返回的 HTML。

查询、写入、任务执行及回调分别检查身份、患者归属和授权。演示身份不代表真实认证；外部模式缺少依赖时拒绝相应操作，不自动退回演示身份。

缺失保留空值及原因。开盒、家属报告、推断和本人报告分别保存。无记录不直接等于未服，时间偏移不冒充真实吞服时间，不伪造改善曲线。

真实设备、自动病历识别、真实药师/家属/志愿者、外部推送及公网部署仍属于外部接入边界。明确紧迫危险按项目配置的优先支持路径处理，不编造已联系或未经核验的求助资源。

## 3 公共数据与接口契约

### 3.1 统一响应与操作标识

接口基线使用 `/api/v1`，以 S00 冻结清单为准。响应统一为 `request_id/status/data/error`，与适当 HTTP 状态一致。

成功示例：

```json
{
  "request_id": "本次请求追踪号",
  "status": "success",
  "data": {},
  "error": null
}
```

失败示例：

```json
{
  "request_id": "本次请求追踪号",
  "status": "error",
  "data": null,
  "error": {"code": "稳定的错误代码", "message": "可读的错误说明"}
}
```

`request_id` 追踪本次请求；`Idempotency-Key` 识别同一业务操作；业务 ID 标识记录。相同幂等键及内容返回同一业务结果，同键不同内容冲突。重试可有新追踪号，但不能重复调用模型、创建申请、扣分或执行。

幂等结果与业务提交保持一致，处理并发、在途及失败。用户消息取得稳定标识后才进入模型；生成重试引用原消息，不重复插入发言。真实接口失败不伪装为空列表、零比例或完成。

模型内部结果转换为平台业务响应；网页不依赖供应商结构，不直接连接数据库。每条记录保留实际来源与模拟标记。

### 3.2 共用字段与对象要求

本节给出 A 与其他模块交接的公共基线。S00 按第 2.2 节补齐本期所需对象、完整字段定义及接口卡，确认后供各模块共同使用；不将远期业务混入本期范围。

以下为建议基线；已有团队约定时以实际约定为准。新增名称和类型在采用前共同确认，本文件版本不代表接口已冻结。

#### 数据从哪里来、交给谁

- 从账号与画像模块取得患者身份、授权、画像和确认计划。
- 从网页、手动填写及设备取得原始记录。
- A 整理记录，返回统计、趋势和状态摘要。
- B 读取需要的数据，返回干预及响应记录，A 汇总其评价信息。
- 社会支持模块的服务、积分和兑换由其维护，A 不另建重复业务。

#### 最少需要统一的字段

| 内容 | 建议字段 | 含义 |
| --- | --- | --- |
| 患者 | patient_id | 患者引用，接口建议使用字符串，不能用家属账号替代。 |
| 用药计划 | plan_id、plan_version | 引用正式计划及版本，由对应模块发布。 |
| 计划时段 | dose_slot_id、scheduled_at | 一次应完成的计划用药及时间，生成方和计数粒度需与计划模块统一。 |
| 原始记录 | event_id | A 保存的唯一记录编号。 |
| 来源 | source、source_event_id | 区分手动、药盒等来源，并识别来源内的重复事件。 |
| 时间 | occurred_at、received_at | 事情发生和后台首次收到的时间。统一使用带时区时间，不混用。 |
| 指标 | metric_code、value、unit | 指标名称代码、数值和单位，数值类型按指标定义。 |
| 缺失 | missing_reason | 值为 null 时说明未采集、设备失败等原因，不能填成零。 |
| 模拟标记 | is_simulated | 是否为演示数据，由实际接入环境校验。 |
| 请求追踪 | request_id | 关联本次请求和错误，不能代替事件编号或去重标识。 |
| 设备 | device_id | 设备引用，需核验可信身份及患者绑定。 |
| 摘要 | summary_id、window_start、window_end、updated_at、data_status | 摘要编号、时间范围、更新时间及可用或不足状态。 |
| 公共执行 | task_id、execution_id、intervention_id | A 的任务及执行编号，关联 B 提供的干预编号，不混成一个标识。 |

服药证据还需统一 evidence_type，至少区分本人确认、家属报告、开盒和设备推断；是否匹配用 link_status 表达。具体代码与已有模块统一，不在各文件中分别起名。

统计结果固定使用 planned_dose_count、patient_confirmed_count、reported_not_taken_count、postponed_count、unconfirmed_evidence_count、unknown_count 和 patient_confirmation_ratio。所有计数字段为整数，比例为 0 到 1 的数值或 null；patient_confirmed_count 仅表示本人明确报告已服，不能包含本人明确报告未服。具体含义见 A6，其他模块直接引用，不另造同义字段。

摘要建议使用 record_overview 引用上述统计，measurement_overview 整理指标，feedback_overview 汇总 B 和社会支持反馈，missing_items 列出不足。具体对象、类型和状态代码与维护方对齐，A5 不另定义同义统计字段。

来源缺失、执行失败、未知回执和模拟结果分别说明。社会支持反馈沿用“支持需求变化、支持接受程度、干预效果”三个维度，不把申请状态当作实际效果。

不是每个对象都包含所有字段。单独定义病历、草稿、服药记录、指标及统计对象的最小输入输出，并写清必填、可空和生成方；网页不能任意设置后台身份或处理结果。

#### 各类数据的状态

用清楚的业务含义表达状态，具体代码统一采用一套：

- 文件：已保存或保存失败，不等于识别完成。
- 草稿：编辑中、待确认、已取得正式确认或被退回。确认结果来自计划维护方。
- 记录：待校验、校验通过、需复核或处理失败。与“是否已匹配时段”分开。
- 统计：可用、待更新或暂不能计算，说明实际原因。
- 执行：待执行、已提交、已完成或失败等按实际渠道定义，不能将已提交认定为患者已收到。

缺失、服务不可用和确实没有数据应分别表达，不把依赖失败返回成空列表或零比例。

#### 接口按什么能力划分

| A 提供的能力 | 输入重点 | 输出重点 |
| --- | --- | --- |
| 病历上传与读取 | 患者、文件、来源 | 文件编号、保存状态、授权读取方式。 |
| 草稿录入与提交 | 结构化内容、草稿修订 | 草稿状态、提交记录及正式计划引用。 |
| 服药与指标记录 | 患者、来源、发生时间和具体内容 | 记录编号、接收及质量状态。 |
| 记录查询 | 患者、日期或范围 | 当前有效记录、必要来源与质量说明。 |
| 用药统计 | 患者、时间范围、数据环境 | 计划时段数、本人已服数、本人未服数、暂时延迟数、仅其他证据数、未知或待复核数和确认比例。 |
| 指标趋势 | 患者、指标、时间范围 | 按实际采样时间排列的数值、单位及缺失说明。 |

| 设备接入 | 可信设备、患者绑定、来源事件及指标 | 接收和质量状态，复用共同处理。 |

具体 URL、方法、分页和调用方式与成员统一后列在同一处，不让每份模块 Prompt 各自规定。

#### 返回结果与重复请求

每个接口给一个最小成功例子和失败例子，并遵守以下已确认的统一约定。

- 同次状态变更提交使用稳定的 `Idempotency-Key`；重试返回同一业务资源，`request_id` 仅用于本次请求追踪。
- 同一来源编号内容不同，报告冲突，不覆盖旧数据。
- 不同来源对同一时段的证据可以并存，统计时再按时段处理。
- 已有其他模块的数据模型先复用，避免同一患者或计划编号出现不同类型。
- 授权撤销后重新检查访问权限，不能从旧缓存继续返回健康数据。

#### 网页联调要求

先确定网页和后端地址、登录凭据与同源或跨域方式。支持文件表单和 JSON 请求，错误不能被替换成网页首页。需要跨域时配置实际允许来源，不以允许跨域代替授权。

网页刷新、多标签重复提交和患者切换都要有明确行为。系统通知为可选能力，拒绝授权或不支持时仍可在页面内查看结果；不默认承诺关闭网页后仍能提醒。

#### 本任务输出与验收

输出一份可分享的简明约定：对象字段表、接口能力与维护方、成功失败样例、还需成员确认的事项。

验收时用两个模拟患者跑通“提交记录—查询—统计”，检查患者隔离、重复提交、缺失值和错误。统计分组及比例详见 A6；不要在这里重新计算画像或规定临床阈值。

### 3.3 标识、时间和版本

- 使用稳定唯一的字符串标识。核心关联包括 `patient_id/case_id/session_id/message_id/assessment_id/intervention_id/suggestion_id/invitation_id/referral_id/request_id`，按需引用 `plan_id/plan_version/dose_slot_id/source_event_id`。
- 区分计划时间 `scheduled_at`、事件发生 `occurred_at`、服务器接收 `received_at`、生成 `generated_at`、有效期 `valid_until`。使用带时区 ISO 8601，统一存储基准，按患者时区展示，本地默认 `Asia/Shanghai`。
- 未知使用 `null` 并保留原因。覆盖情况按指标分别定义，缺失不当作零，不直接当作漏服。
- 数据结构、提示词、知识、评估方法、规则和模型配置各有版本。一次决策固定输入快照及版本引用；不要依赖事后变化的当前配置解释旧结果。
- `mode=real/mock` 只表示模型调用来源；`ui_mode=normal/simplified` 只表示界面状态。外部数据和渠道另有来源及模拟标记，避免一个布尔值掩盖整条链路的来源。

### 3.4 A 提供的最小状态摘要

约定 `patient_id`、`summary_id`、时间范围、生成/有效时间、`data_status=fresh/stale/insufficient`、不足项、计划版本引用、数据来源与指标。

用药记录统一读取 A 的本人确认已服、本人报告未服、暂时延迟、仅有其他证据、未知或待复核五类结果，字段沿用 patient_confirmed_count、reported_not_taken_count、postponed_count、unconfirmed_evidence_count、unknown_count，并读取 planned_dose_count 与 patient_confirmation_ratio。确认比例仅计本人已服，不代表客观吞服率或 CAS。未知或待复核保留原因，延迟后的结果更新由 A 处理；B 不自行重新分类计数或另算比例。

其他指标可包括睡眠、活动和生理变化。每项保留值、单位、采样时间、覆盖口径及来源引用；没有的字段不编造。

摘要过期或不足时，B 按明确规则刷新、询问、暂不决策或进入专业复核，保留原因。明确规则前不把单次生理变化或缺失判断为心理疾病或高风险。

### 3.5 B 返回给 A 的干预记录

包含患者、会话、干预事件、触发来源、输入证据引用、支持类型、支持强度、交互负担、建议渠道、决策理由摘要、规则/提示词/知识版本、决策时间、执行状态、展示回执及用户响应。

理由摘要是可核对的业务证据和规则说明，不保存或展示模型内部思维链。

## 4 O 账号、问卷、画像、用药与提醒

本章由原 01 业务整合而来。与其他章节的公共工程、知识和导航要求均以总约束为准。O 负责正式计划及画像维护，A 保存引用和证据，不重复发布另一套计划。

### O1 患者与家人双模式

#### 身份选择与使用入口

首次进入平台时，提供“管理自己的用药”和“帮助家人管理用药”两个入口。

患者模式以个人用药计划、日常提醒、依从性评估和个人设置为核心；家人模式以已绑定患者的用药信息查看、协助管理和权限内操作为核心。

允许同一账号既管理自己的用药，又协助管理其他家庭成员，不应将患者与家人设置为永久互斥的身份。

用户再次进入时保留上次使用状态，支持随时切换本人及家庭照护对象。

#### 家庭绑定与数据权限

通过用户 ID 或绑定码实现患者与家人账号关联。

患者有权决定：

- 是否绑定家人。

- 允许家人查看哪些用药资料。

- 是否共享服药记录和画像摘要。

- 是否允许家人协助编辑药品资料、用药计划及提醒设置。

- 是否允许家人接收相关通知。

- 是否解除绑定或撤销授权。

家人端展示内容必须与实际授权相符，不能因为建立家庭关系就默认获得全部健康信息。

支持一位患者绑定多位家人、一位家人管理多位患者，并明确区分当前正在管理的对象。

#### 本人作答与家人代答

基础问卷支持“本人作答”和“家人协助作答”。

对于不方便独立操作的老年人或其他需要帮助的患者，家人可以协助完成问卷，但应明确当前评估的对象是患者本人，而非家人。

对于“担心副作用”“是否认可服药必要性”“是否愿意让他人知道自己用药”等涉及患者主观感受的问题，家人不能替患者随意推定答案。

当家人不了解患者真实想法时，应允许选择“不清楚”，并对结果作出适当提示。

家人代答不等于获得患者的全部数据授权。数据共享仍应遵循患者授权及适用的监护规则。

### O2 简短问卷

#### 问卷定位

平台中的依从性评估应当与团队既有的《药物依从性影响机制报告》建立实质联系。

既有研究已经形成了以 CAS 为目标的药物依从性预测体系，重点涉及：

- F1：依从性抵触倾向。

- F2：药物负担感知。

- F3：生活规律性。

- 自我效能。

- 技术接受。

- 健康素养。

- 复诊规律、药物复杂度及相关背景信息。

网页应尽可能复用已有研究成果，结合患者填写的基础信息及用药资料，形成初步依从性估计。

但原研究中的量表和模型输入信息较多，不能假定缩短后的八道题天然等价于原始量表。开发时需要保证原模型输入与当前问卷数据之间具有经过核对的对应关系；如果当前信息不足，应如实显示评估条件尚不完整，不得生成伪造的模型预测。

另外，原模型主要用于估计依从性水平，而患者具体不依从的原因需要结合补充问题进一步分析。

因此，将简短问卷设计为兼顾模型相关信息采集和具体障碍识别的交互流程。

#### 问卷整体交互

整份初始问卷严格控制在八个主题问题以内。

不采用连续八道普通单选题，而是根据不同问题的特点，组合使用：

- 情境式选项卡。

- 简短程度量表。

- 多选标签云。

- 重要程度排序。

- 条件展开的补充选择。

每个问题围绕一个明确主题，不用多个复杂问题伪装成一道题。

尽量通过一个交互页面获取多个相关信息，但不应增加明显的认知负担。

用户每次只需关注当前问题，回答后平滑进入下一步。支持返回修改、保存进度，以及对不适用问题选择“无法判断”。

问卷措辞贴近实际生活，避免直接向患者展示 F1、F2 等研究术语。

#### 八道核心问题

**Q1｜最近一个月，你的实际用药情况更接近哪一种？**

采用情境选择卡片，选项例如：

- 基本能够按照医嘱服药。

- 偶尔延迟，但通常不会忘记。

- 有时因为忘记而漏服。

- 有时因为个人想法或顾虑而主动推迟或停止服药。

- 不太确定自己的用药情况。

允许对同时存在的情况进行补充选择。

这一问题用于获取患者对近期用药行为的自我报告，帮助区分基本稳定、无意偏离和主动改变计划等情况。

不得将患者自报结果直接当作客观服药验证数据。

**Q2｜哪些事情最容易让你难以坚持用药？**

设计为可交互的原因标签云 + 重要性排序。

页面中提供多个清晰可读的标签，例如：

- 容易忘记

- 作息不规律

- 工作学习太忙

- 出门不方便吃药

- 药太多、步骤麻烦

- 不清楚怎么服用

- 药品没有及时补充

- 担心副作用

- 担心长期服药的影响

- 认为没有症状就不必吃药

- 感觉治疗效果不明显

- 服药时间久了感到厌倦

- 压力大、没有精力

- 不希望被别人发现

- 购买药品不方便

- 经济负担较重

用户先选择符合自身情况的标签，再从已选标签中选出最重要的三项并排序。

允许选择“以上都没有”或填写简短的其他原因。

注意：这里的“词云”主要是便于选择的视觉化标签集合，不应将预设标签大小伪装成真实研究统计结果。

这一题重点帮助系统识别患者的主要障碍、次要障碍及主观重要程度，为后续细分类型提供依据。

**Q3｜当身体感觉好转，或者没有明显症状时，你通常怎样看待继续服药？**

采用情境式单选卡片，例如：

- 我仍认为需要遵照医嘱坚持服药。

- 我知道需要继续，但偶尔会怀疑是否有必要。

- 我有时觉得可以少吃一点或暂时不吃。

- 我曾因为感觉好转而自行调整或中断服药。

- 不清楚或不适用。

这一题关注患者对持续治疗必要性的认知，以及主动改变用药计划的倾向。

注意区分“有过疑问”和“已经自行停药”，不能把两者视为完全相同的行为。

**Q4｜对于目前的用药，你最担心哪些事情？**

采用多选卡片与担忧程度选择相结合的形式。

可选择：

- 药物副作用。

- 长期使用对身体的影响。

- 是否会产生依赖。

- 药物是否真正有效。

- 疾病可能进一步恶化。

- 长期用药的经济成本。

- 不太担心上述问题。

对于选择的项目，允许用户标出最担心的一至两项。

这一题主要补充药物负担感知及具体顾虑内容，并帮助区别副作用担忧、治疗信心不足、经济压力等不同原因。

不要因为用户表示担忧较多，就直接认定其依从性一定较差。

**Q5｜在什么情况下，你最容易错过原定的服药时间？**

采用生活场景卡片，可多选：

- 起床或睡觉时间经常变化。

- 三餐时间不固定。

- 轮班、夜班或工作学习安排变化。

- 出差、旅行或长时间外出。

- 正在开会、上课或社交。

- 临时忘记携带药品。

- 一般不会受到这些情况影响。

可以配合简单的频率选择，帮助了解生活节律的稳定程度。

这一题既服务于原研究中生活规律性相关信息的采集，也帮助后续推荐不同作息模式和隐私提醒方式。

**Q6｜即使遇到忙碌、疲惫或日程变化，你有多大把握能够继续按医嘱完成用药计划？**

采用五级信心量表：

- 完全没有把握。

- 不太有把握。

- 一般。

- 比较有把握。

- 非常有把握。

这是与原研究自我效能维度相联系的重要问题。

用语应强调患者的自我管理信心，而不是评价其是否足够自律。

**Q7｜在理解和执行当前用药安排时，你最需要弄清楚什么？**

采用多选卡片，例如：

- 为什么需要长期服药。

- 每种药具体有什么作用。

- 每次该服多少、如何服用。

- 服药时间与吃饭、睡觉有什么关系。

- 漏服或延迟时应该如何处理。

- 什么时候需要复诊或咨询医生。

- 目前基本清楚，不需要额外解释。

这一题补充健康素养、用药认知和实际操作困难等信息，帮助区分“知道应该服药但做不到”和“不理解为什么或怎样服药”。

同时允许展示用户最想了解的内容，为药学知识支持模块提供个性化入口。

**Q8｜如果平台能够提供帮助，你最希望获得哪些支持？**

采用帮助方式选择卡片，并允许按优先程度排列。

选项例如：

- 到时间提醒我。

- 将服药提醒与起床、吃饭等日常习惯结合。

- 在外出或忙碌时采用更合适的提醒方式。

- 用不暴露药品和疾病信息的方式提醒。

- 用简单易懂的语言解释用药知识。

- 帮我把复杂的用药计划整理清楚。

- 在坚持服药感到疲惫时提供适当支持。

- 在我同意的情况下，让家人给予帮助。

- 暂时不需要更多提醒或帮助。

可以选择最需要的三项，排列优先顺序。

这一题主要了解患者对数字化支持方式的接受程度、家庭协助偏好和个性化服务需求。

这里收集的是用户偏好，不应直接代替对实际依从性水平的估计。

#### 问卷体验细节

- 首次填写前，用简短文字解释评估用途。

- 预计填写负担应较低，不要让患者面对密集的医学量表。

- 根据患者前面已选择的内容，减少后面重复或无关的选项。

- 对“无”“不适用”“不了解”等回答进行明确区分。

- 对家人代答的主观问题提供“不清楚”选项。

- 标签云需清晰可点击，选中状态明显。

- 重要程度排序支持拖动；对于不便拖动的用户，也提供简单的顺序调整方式。

- 不必要求每道题都填写大量补充信息。

- 问卷提交后提供清楚的结果反馈，而不是突然跳转到复杂的数据仪表盘。

- 支持用户以后重新填写或更正回答。

首次问卷之外，药物种类、服药频次、处方要求等已经在用药资料中存在的信息应尽可能直接复用，不让患者反复填写。

复诊规律、用药时长及其他原模型需要的背景信息，可在已有资料中补充和管理，但不应为了凑齐变量而增加大量隐藏的必答问卷。

### O3 依从性估计与患者分类

#### 两个相互联系但不同的评估结果

平台的评估结果应体现两个层次。

第一层：药物依从性水平

以团队已有的 CAS 研究及相应预测模型为基础，对患者的依从性水平进行估计。

该结果代表模型预测，不等于已经客观证实的真实服药率。

对于数据不充分、模型尚未适配或预测不确定性较高的情况，应提供适当说明，不得凭空生成精确指数。

第二层：主要不依从障碍

结合问卷中的情境、原因、主观排序和相关信息，判断患者为何可能难以坚持用药。

两者共同形成用户画像。

例如，一位患者即使目前依从性较高，也可能存在副作用顾虑；另一位患者虽然依从性较低，主要问题却可能是工作时间不规律，而非缺乏治疗意愿。

因此，依从性水平不能直接代替不依从原因分类。

#### 患者分类体系

采用本文件 O3 列出的分类框架；该框架依据原《网页设计核心逻辑.pdf》并已统一，不自行增加其他平行类型。

A. 高依从性患者：维持型

特点是目前用药执行相对稳定。

平台重点提供方便、适度的用药支持，保持既有习惯，不应因为使用健康管理产品而增加大量无意义的操作。

B. 无意不依从

包括两个子类型。

B1. 遗忘与习惯缺失型

主要涉及忘记服药、缺少稳定提醒线索、难以形成用药习惯，以及作息变化导致的漏服。

B2. 操作与外部条件受限型

主要涉及用药流程复杂、不清楚如何安排多种药物、药品未及时补充、取药不方便或其他实际操作障碍。

需要区分单纯记忆困难与客观执行条件不足。

C. 有意不依从

包括三个子类型。

C1. 用药认知不足型

患者可能不清楚治疗目的、缺乏对长期服药必要性的理解，或对用药方法存在认识不足。

C2. 用药顾虑与心理抗拒型

患者可能担心副作用、长期毒性或药物依赖，对治疗效果缺乏信心，或者因相关顾虑主动减少和中断服药。

C3. 情绪低落与用药疲劳型

长期服药可能让患者产生厌倦、疲惫、抵触或持续管理负担，情绪和精力状态也可能影响其坚持用药。

本模块只负责识别问卷中反映的相关困难，不进行精神心理疾病诊断。

D. 有意与无意因素兼有

D1. 社会情境与生活冲突型

患者可能由于工作、差旅、社交场合、隐私顾虑和日常生活安排等因素受到影响。

其中既可能存在客观时间或环境限制，也可能存在不愿公开用药等主观因素。

#### 复合画像

分类结果不应强制每位患者只能拥有一个绝对固定的标签。

例如，一位患者可以同时出现：

- 遗忘与习惯缺失。

- 社会情境与生活冲突。

- 一定程度的用药顾虑。

页面优先展示当前最值得关注的主要类型，同时允许显示其他相关因素。

对高依从性患者，也可以展示其潜在的支持需求，但不应仅因存在某项顾虑就将其划入低依从性人群。

分类结果允许随重新评估而变化。

#### 画像结果页面

问卷结束后，进入专门的评估结果页面。

建议内容包括：

个人依从性概况

直观展示目前可用的依从性评估结果，区分模型估计和用户自我报告。

主要影响因素

例如：

“根据你的回答，忙碌和作息变化可能是影响用药安排的重要原因。”

个人关注重点

以简洁的排序标签展示用户认为最困扰自己的两至三项问题。

对应支持建议

根据画像类型，提供与本模块实际功能对应的入口，例如：

- 开启用药提醒。

- 设置起床或睡前提醒习惯。

- 整理复杂的药物清单。

- 查看药品说明及注意事项。

- 开启隐私提醒。

- 设置外出或夜班模式。

对于需要心理沟通、社会支持等其他功能的情况，只需提供与相应模块连接的入口，不在本模块重复开发。

用户端不应展示大量研究术语、模型参数或难以理解的技术图表。

可以保留清晰、直观的视觉化画像摘要，使患者理解结果如何与自己的实际情况相关。

### O4 用药计划与初步药学支持

#### 用药计划建立

患者可以通过已有的病历资料、处方信息或手动录入方式建立个人用药计划。

支持展示并核对：

- 药品名称。

- 每次服用剂量及单位。

- 每日或每周服用频次。

- 用药时间。

- 开始与结束日期。

- 是否有餐前、餐后或其他特殊要求。

- 医嘱中需要特别注意的内容。

病历或处方识别结果必须经过用户确认，不能把未经核对的信息直接作为正式用药计划。

允许用户对录入错误进行修正。

涉及改变处方剂量、服药频次或治疗方案时，应提示按照医生或药师的专业意见处理。

#### 日常用药管理

形成清晰的个人药品清单与今日用药日程。

药品管理页面支持：

- 查看已有药品。

- 添加或编辑药品资料。

- 查看某种药物的服用安排。

- 查看当天待确认的用药任务。

- 对服药情况进行确认。

- 查看已设置的提醒。

重点解决多种药物安排复杂、用户不清楚何时服用等问题。

不同药品的任务状态应清晰区分。

不能将“用户没有点击确认”直接等同于“已经漏服”。

#### 药学科普与生活方式建议

依据用户实际药品信息，提供简洁、可靠的药学知识支持，包括：

- 药物的基本用途。

- 常见注意事项。

- 有明确依据的饮食要求。

- 与服药时间相关的生活方式建议。

- 需要咨询医生或药师的情况。

优先以已经核实的药学资料和实际医嘱为依据。

本模块负责药品知识页面、个性化内容展示及专业咨询入口。药学资料统一引用 B2 提供的共用资料与来源，不另建一套独立知识库。实际医嘱以经确认的用药计划为准，知识展示不得替代或修改医嘱。

不同患者可以根据画像看到不同的重点内容：

- 用药认知不足型：强调药物用途与规范用药知识。

- 操作与外部条件受限型：强调服药安排的清晰性与便捷性。

- 用药顾虑与心理抗拒型：突出可信赖的药品知识和专业咨询入口。

- 其他类型：展示与其实际困难相关的必要信息。

不要简单地对所有患者展示同一套健康知识。

所有建议应避免未经依据的停药、换药或调整剂量指导。

### O5 个性化用药提醒

#### 基础提醒与自主设置

依据患者已经确认的用药计划建立相应提醒。

允许患者自主选择适合自己的提醒方式。

根据平台实际支持的能力，可以提供：

- 应用内提醒。

- 可授权的系统通知。

- 声音或振动提醒。

- 稍后提醒。

- 自定义提醒文字。

- 隐私模式。

用户可以随时修改提醒偏好。

提醒方式应以实际设备和平台支持的功能为准，不应展示已经成功发送但实际无法送达的通知。

#### 生活节律事件锚定提醒

针对作息不规律、轮班、夜班、出差等人群，提供比单纯固定时间更灵活的提醒设置。

支持用户选择：

- 常规作息。

- 夜班作息。

- 轮班作息。

- 外出或差旅模式。

- 自定义生活作息。

允许将提醒与起床、早餐、睡前等日常事件关联，帮助患者形成较稳定的用药习惯。

如果其他模块已经提供可靠且经过授权的睡眠、活动或情境信息，本模块可以使用这些结果辅助推荐提醒时机。

未获取相关数据时，应使用用户主动设置的作息信息，而不是假装具备实时感知能力。

特别注意：提醒方式的适应性不意味着可以随意改变医嘱规定的服药时间。

对于具有严格服药间隔、固定时间或进食要求的药物，必须优先尊重医学约束。

#### 隐秘社交护盾（Stealth Social Mode）

考虑部分患者不愿在工作、学习或社交场所公开自己正在服药的情况，提供隐私友好的提醒方式。

用户可以自主开启隐私模式。

隐私模式下，尽量避免在通知中直接展示药品名称、疾病名称或其他敏感信息。

提醒文字可采用：

“今日事项待确认。”

“有一项日程需要处理。”

也可以由用户自行设置。

支持按时间段或外出模式切换提醒偏好。

当用户处于公共场所或其他不方便公开用药的情境时，可以主动切换至低打扰模式。

如果其他模块能够提供有效的返家状态信息，可在用户授权后提供相应提醒；如不具备真实返家检测能力，则允许用户手动结束外出模式。

返家后的补充提醒仅用于提醒患者核对尚未确认的任务，不等于建议患者立即补服药物。

#### 通知疲劳管理

避免传统提醒工具出现的反复催促和过度打扰问题。

对于已经确认完成的任务，应停止无意义的重复提醒。

对于历史记录相对稳定、仅因偶发日程冲突延迟确认的用户，可以推荐减少不必要的重复通知。

用户应能够控制提醒的重复频率及强度，并随时恢复原有设置。

不应因为患者过去表现稳定，就自动取消医学上必要的提醒。

同时，需要区分：

日常用药状态与 A 的统一统计口径对应：

| 统计类别 | 含义 | 字段 |
| --- | --- | --- |
| 本人确认已服 | 本人明确报告该时段已经服药。 | `patient_confirmed_count` |
| 本人报告未服 | 本人明确报告该时段未服药。 | `reported_not_taken_count` |
| 暂时延迟 | 本人表示暂时延后，尚无后续结果。 | `postponed_count` |
| 仅有其他证据 | 有开盒、家属报告或设备推断，但无本人明确状态。 | `unconfirmed_evidence_count` |
| 未知或待复核 | 证据不足，或存在尚未解决的冲突；附原因。 | `unknown_count` |

网页读取 A 的统一结果，不另算确认比例。

五类按计划时段互斥统计，总数等于纳入统计的计划时段数。证据原文和历史仍分别保存。

患者确认比例＝本人确认已服时段数÷有效计划时段数。明确未服和暂时延迟不计入分子；这一比例仍是本人报告口径，不代表客观验证的吞服率，也不是 CAS 预测值。

延迟后补充明确结果时，更新当前分类，不重复增加计划时段。矛盾证据保留原因并进入待复核，不能静默覆盖或显示为普通“无记录”。

不同情况应给予适合的提示，不使用指责、催逼或令人焦虑的措辞。

#### 提醒方式与用户画像联动

不同画像对应不同的提醒支持重点。

维持型

保持简单、适度、稳定的提醒，不增加额外负担。

遗忘与习惯缺失型

优先提供规律提醒、习惯关联及容易完成的确认方式。

操作与外部条件受限型

优先帮助用户整理服药安排，使多个药品的任务更加清晰。

用药认知不足型

结合必要的药学信息和清晰提醒，帮助患者理解用药计划。

用药顾虑与心理抗拒型

避免一味增加提醒次数，优先提供药学知识和进一步支持的入口。

情绪低落与用药疲劳型

保持提醒操作简单，减少不必要的干扰。

社会情境与生活冲突型

突出隐私提醒、灵活场景设置与生活节律适应。

这里的联动主要体现为用户可见的功能推荐和提醒偏好，而不是由本模块独立完成全部 AI 心理干预或社会支持服务。

## 5 A 数据与公共后端

本章复用第 3 章公共契约。A 的任务和投递只负责公共执行，业务触发与状态的维护方按总约束区分。

### A0 公共基础工程

请在总约束和公共契约下，建立 O、A、B、C 共用的 Python 后端基础工程。A0 负责后端底座，统一网页外壳按 S01 和第 8 章建立，不另建独立前端工程。

#### 开发目标

后端可以启动，读取配置，接收请求，返回统一结果，并让后续数据模块使用同一套数据库连接、日志和身份授权入口。

基础工程采用上文已确认的 FastAPI、SQLite 和统一网页服务基线，供 O、A、B、C 共同接入。优先复用已有统一工程；尚未确定的目录细节在同一工程内约定，不分别生成独立应用。

#### 需要接收的输入

- 团队技术选型、项目目录与已有代码。
- 第 3 章及 S00 冻结契约中确定的请求响应及患者授权方式。
- 账号模块提供的身份、家属授权及服务调用方式。
- 本地开发或测试环境信息。

外部模块未就绪时，可使用明确标注的模拟适配，真实服务失败不能悄悄改用模拟身份。

#### 基础功能

1. **应用入口**：明确启动、关闭及模块接入方式，不在导入代码时执行投递、建表或后台任务。
2. **配置**：统一管理环境、数据库地址、日志、外部接口及模拟开关；配置示例不含真实密钥。
3. **数据库连接**：后续模块共用连接和会话方式，操作失败回滚并释放资源；业务表结构与迁移由 A1 统筹。
4. **日志与错误**：记录 request_id 和操作结果，返回统一错误，不把密钥、完整病历和内部堆栈返回网页。
5. **身份授权**：区分当前账号和目标患者，查询及写入都检查权限，不根据请求体自报身份放行。
6. **运行检查**：能区分进程仍在运行和必要依赖是否可用，依赖失败不假装业务已就绪。
7. **模块接入**：A、B 按同一方式接入，重复接口或操作名能被发现，不静默覆盖。

#### 网页怎样调用

提供后端地址、启动方式和一个最小请求示例。按团队实际登录及部署方式处理会话、跨域或代理；API 不存在时返回约定错误，不能回退成网页首页。

使用 Cookie 会话时处理相应状态变更请求防护；使用其他凭据时按共同约定处理。不在本任务自行新增一套账号系统。

#### 输出结果

输出可运行的基础代码、依赖与配置示例、启动和测试说明，以及后续模块接入位置。目录保持简单，共同定义集中维护，不为未实现功能建立大量空文件。

本任务交付基础工程代码。数据库迁移、数据业务、模型、调度及投递分别在对应模块实现。

#### 验收

- 按说明启动后可调用基础接口。
- 配置错误和数据库不可用时有清楚反馈。
- 请求及异常能通过 request_id 关联。
- 模拟患者甲不能读取乙的数据；家属授权撤销后访问被拒绝。
- 生产环境不能使用模拟身份，真实认证失败不自动放行。
- 应用关闭后资源被释放，导入或启动不自动建业务表、投递或训练。

说明实际验证了什么、哪些依赖是模拟，不把骨架运行成功描述成所有业务已完成。

### A1 数据存储与迁移

请为 A 部分建立清楚、可复用的数据存储结构，让后续录入、清洗和统计使用同一套数据。遵守总约束、公共契约和实际已建立的 A0 工程。

#### 模块目标

保存病历、录入草稿、服药证据及生理指标，保留来源和必要历史；支持查询、重复检查、统计及后续摘要。

使用团队确认的数据库和访问工具，不在本模块另选一套。按本次确认范围建立模型和迁移。

#### 需要哪些数据

| 数据 | 需要保存的内容 |
| --- | --- |
| 病历文件 | 患者、文件编号、受控存储引用、类型、来源、时间和状态。 |
| 录入草稿 | 患者、来源文件或手工来源、结构化内容、修订及确认状态。 |
| 正式计划引用 | 对应模块发布的计划编号、版本、有效区间和必要快照。 |
| 计划时段 | 已统一的时段编号、患者、计划条目和应服时间。 |
| 服药证据 | 本人确认、家属报告、开盒或推断的原始来源和发生时间。 |
| 生理或行为指标 | 指标、值、单位、测量时间、来源和缺失原因。 |
| 处理与更正 | 质量结果、更正原因、原记录和当前有效修订。 |
| 统计及摘要 | 按需要保存结果、时间范围、更新时间和依据版本。 |
| 公共执行 | 后续调度及投递需要的任务、执行结果和关联编号。 |

只建立本期实际需要的结构。公共执行及 B 的表在字段明确后集成，不提前猜测全部业务。

#### 谁维护什么

- 身份、家庭授权、画像和正式计划归对应模块。A 保存引用，不建可独立修改的第二套事实。
- A 维护原始数据、清洗、统计及公共执行的存储。
- B 定义会话、心理评估、干预及响应的业务字段，A 统一集成已确认的表结构。
- 网页通过后端访问，不获得数据库凭据或服务器存储路径。

跨服务对象不能假设存在本地外键；同库结构及外部引用分别说明如何验证归属。

#### 数据怎样关联和保存

1. 记录始终关联实际患者，计划和证据不能跨患者串用。
2. 来源编号与 A 的记录编号分开；同一来源事件不能重复保存为多个有效事实。
3. 一个时段可有多条来源证据，时段本身不因此增加。
4. 缺失用 null 并注明原因，不设置会把缺失变成零的默认值。
5. 保留发生、接收和更新时间，计划版本及更正不能静默覆盖历史依据。
6. 模拟与真实数据可区分、可单独查询，不能混入同一未声明统计。
7. 对患者近期记录、指标趋势、来源去重和时段关联建立必要索引，不为每个字段机械建索引。

时段由谁生成、按药物条目还是按合并行为计数，需要与计划模块统一后落实。

#### 数据库更新方式

提供统一的建库或迁移入口、版本记录和使用说明。已有数据时先检查影响，再通过新的结构变更升级，不覆盖别人已经使用的历史迁移。

新字段、非空或唯一约束需考虑现有数据，不能为了升级通过清空记录。普通应用启动不自动删除、重建业务表。

一期先支持空库建立和必要升级；复杂分支合并、完整历史回放等作为后续完善内容，需要时按后续明确的扩展任务完善。

#### 输出与验收

输出模型、数据关系及字段说明、初始化或迁移文件、虚构测试数据和运行说明。

验证：能保存并查询两名患者的数据；重复来源记录受到约束；一个时段可关联开盒和确认两条证据；缺失与零不同；更新结构后原数据仍在；失败事务不会留下半条业务记录。

本模块完成存储基础，不意味着上传接口、清洗或统计已经实现。必要结构由后续模块提出后统一补充。

### A2 病历与手动数据接收

请在共同后端基础上实现病历上传、人工结构化录入和手动记录接收，让网页提交的数据能够保存、查询，并交给后续清洗和统计使用。

#### 模块目标

跑通两条流程：

病历上传或手工建档 → 人工核对资料 → 提交确认 → 保存正式计划引用。

手动填写服药或指标记录 → 保存来源与时间 → 返回接收结果 → 交给 A4 处理。

自动识别病历和真实设备接入暂不要求。本任务需要交付能保存和查询数据的后端代码。

#### 输入与已有数据

- 当前患者及操作者身份、实际授权。
- 病历文件，或人工录入的用药资料。
- 正式计划模块提供的草稿字段、确认方式及计划版本。
- 手动服药确认、生理或行为指标和发生时间。
- 公共契约的字段、A0 的身份及错误处理、A1 的存储结构。

药品名称、剂量单位、频次、时间和特殊医嘱等字段复用计划模块约定，不由 A 另造一种结构。纯手工录入可以没有来源文件，但应明确其手工来源。

#### 业务流程

**1 病历上传**

网页选择文件后，后端检查权限、格式和大小，保存文件与记录，返回文件编号和保存结果。原文件名只作显示，不用它直接拼接服务器路径。

文件只能在授权范围内读取，不通过公开目录向任何人暴露。保存中断或数据库失败时，不能报告完整成功，也不能误删其他文件。

文件上传完成只说明文件已保存，不代表已经识别出医嘱或确认用药计划。

**2 人工录入与确认**

允许将病历中的信息录成草稿，也允许纯手工录入。网页可以查看、修改和再次提交草稿，后台保留修订。

提交的是某个明确修订的内容。通过计划模块的确认流程取得正式计划及版本，A 保存引用；未核对资料不能直接用于提醒和统计。

上传成功、提交成功、正式确认是三个不同结果。确认依照计划模块的权限和流程取得，不要求凭空接入尚不存在的医院审核服务，也不允许网页任意提交一个“已确认”标志作为依据。

上游未接入时，可以模拟提交和确认回传，但必须标为演示。超时保持待确认或结果未知，不假装完成。

**3 手动服药记录**

保存当前患者、本人或家属报告来源、发生时间、来源编号及已有计划时段引用。家属报告不能伪装成本人确认。

同一表单重试返回原记录；不同来源的开盒和本人确认可以并存。网页填了时段编号也需检查归属，不能直接判定匹配成功。

**4 手动指标记录**

保存指标、值、单位和测量时间。缺失保留为空及原因；未知单位或无时区时间不能猜测补全。心理问卷和心理分数由相应模块处理，不混入普通指标。

#### 与清洗模块交接

A2 接收原始记录并做必要格式与权限检查，A4 统一处理单位、质量、冲突和更正。两者共用接收去重能力，不分别建两套原始事件。

记录可以先处于待校验；接收成功不等于已经可计入统计。更正原始数据通过统一更正流程，不用普通编辑抹去旧依据。

#### 输出及网页反馈

提供文件上传读取、草稿录入提交、记录新增查询等接口，沿用公共契约的格式。网页能够看到保存、待确认、需修改或处理失败等真实状态。

登录失效、无权限、重复内容冲突和保存失败有清楚提示。刷新、多标签或患者切换不能导致重复记录或将结果写到另一患者。

#### 验收

1. 上传一份虚构病历，能够授权读取，其他患者不能读取。
2. 修改草稿后提交，能够区分待确认和已取得正式计划引用。
3. 重复上传或重复提交同一事件，不重复生成有效记录。
4. 更换患者、家属代填或撤销授权时，身份与范围处理正确。
5. 输入缺失指标或无效单位，不被自动改成零或正确值。
6. 文件保存失败或确认服务超时，不返回虚假的完成结果。

交付可运行后端代码、调用示例及测试结果，说明哪些确认和外部服务是模拟。不要只输出流程说明或无法保存查询的假接口。

### A3 设备接入与模拟器

请为药盒和可穿戴设备提供统一接入方式，并建立可重复使用的模拟器，让没有真实硬件时也能验证数据进入后端、清洗、统计和摘要的流程。

#### 模块目标

确认设备与患者关联 → 生成或接收设备事件 → 使用公共接收入口 → A4 清洗 → A6 统计及 A5 摘要更新。

一期以模拟数据为主，不要求连接真实设备云服务。接入位置保留，之后替换协议适配即可，不改其他模块的业务字段。

#### 输入

- 设备编号、来源和可信设备身份。
- 已确认的设备与患者绑定关系。
- 来源事件编号、发生时间、事件类型或指标值和单位。
- A1 存储、A2/A4 公共接收规则及模拟环境配置。

设备不能仅在请求体里填写患者编号就写入该患者数据。绑定的维护方和核验方式与团队统一，账号和家庭授权仍归原模块。

#### 接入逻辑

**1 药盒事件**

接收开盒等实际可报告的事件，保留设备、来源编号和时间。开盒证据不直接转成本人确认，也不默认代表盒内所有药物均已服用。

能否关联某个药物条目或计划时段，取决于设备实际提供的信息；没有依据时留给 A6 按统一规则匹配，不能伪造精确关联。

**2 可穿戴数据**

只接收已定义的睡眠、活动和生理指标。值、单位、方法和采样时间按共同约定提供，缺失明确标记。心理状态不由设备接入层自行诊断。

**3 公共处理**

设备协议先适配成共同数据对象，再走 A4 的统一处理。来源内编号保持稳定，重复发送不新增有效事实；同编号内容不同则返回冲突。

离线上传保留实际发生时间，不移动到接收当天。新增或迟到数据通过已有更新机制影响统计和摘要，不在本模块另写一套算法。

#### 模拟器怎样工作

提供简单脚本或受控测试入口，可选择模拟患者、设备、事件时间和场景。无需为它额外开发复杂设备管理网页。

至少支持：

1. 正常药盒开盒。
2. 同一事件重复上传。
3. 延迟上传的事件。
4. 正常指标、缺失指标和未知单位。
5. 未绑定设备或患者不符的请求。

模拟数据标记 is_simulated，并按环境与真实数据区分。固定场景可重放，重放相同事件保持来源编号，不能每次换编号让重复检测失效。

#### 输出与演示

返回事件或指标编号、接收结果、质量问题及必要来源。网页可以通过已有记录、统计和摘要接口查看变化，不把上传成功显示成实际服药已证实。

真实设备不在线时展示未接入或演示状态。后端接收失败应有明确原因，不能仍显示设备同步成功。

#### 验收与交付

- 一条模拟开盒事件可以查到，类型仍是开盒。
- 重复上传后有效事件数不变；独立来源证据可以并存。
- 缺失指标不变成零，未知单位进入统一质量处理。
- 未授权设备或跨患者绑定请求被拒绝。
- 延迟事件能进入原对应时间的处理流程。
- 模拟数据与真实来源隔离，重放结果可以解释。

请交付设备适配入口、模拟器、场景说明、调用示例和实际验证结果。说明真实硬件尚未接入，不输出虚构的设备连通证明。

### A4 数据清洗与质量检查

请接收 A2 及未来设备模块保存的原始记录，统一整理时间、单位、来源及数据质量，并向匹配统计和状态摘要提供可解释的数据。

#### 模块目标

原始记录 → 检查重复和来源 → 标准化时间单位 → 标明缺失或需复核 → 保存处理结果 → 交给 A6、A5。

原始证据应保留；清洗不意味着改成正常值，也不负责生成画像、心理风险分数或调整用药计划。

#### 输入

使用公共契约的共同字段和 A2 的原始记录：患者、来源和来源编号、发生与接收时间、值及单位、计划引用、报告者与模拟标记。

复用 A1 存储及 A2 已有的公共去重入口，不把收到过的数据再复制成另一套事实。所有来源共用规则，只有设备协议适配等必要差异由设备模块负责。

#### 处理逻辑

**1 重复与冲突**

同一事件重复提交只保留一个有效事实。来源编号相同但内容不同，报告冲突，不覆盖原记录。

同一时段先有开盒、后有患者确认是两种证据，应同时保留，不当作重复删除。时间接近、文字相似不能作为自动合并不同来源的唯一理由。

**2 时间整理**

区分实际发生与首次接收时间，将合法的带时区时间统一表达。无时区或无效日期要说明问题，不猜时间。

迟到上传仍按实际发生时间保留，不挪到上传当天，也不因迟到直接丢弃。重复处理不能改写首次接收时间。

**3 单位与数值**

按已确认的指标及单位表转换，保留原值原单位。未知单位或测量方法不兼容时标为需复核，不猜测转换。

缺失、零和错误文本分别处理，不自动均值填补、截断或改成正常值。技术错误不等于临床异常，不自行设置医学危险阈值。

**4 来源和引用**

核对患者、来源及计划归属，家属报告与本人确认保持区分。不能将证据静默改挂到最新计划，也不能代替 A6 根据最近时间强行匹配。

**5 更正与撤销**

允许经过授权的更正，并保存原记录、更正原因、当前有效修订及时间。旧页面不能无声覆盖新修改，撤销不等于删除全部历史。

数据修正或迟到可能影响已有结果时，记录变更并通知 A6、A5 更新；发生时间变化时考虑旧新两个范围。

#### 输出

每条记录返回处理状态、可用结果及原因：

- 待校验：尚未完成处理。
- 校验通过：可交给对应后续用途，不代表已经匹配或实际服药。
- 需复核：存在单位、引用、来源或其他质量问题。
- 处理失败：程序或外部依赖异常，可按规则重试，不直接认定患者数据错误。

具体代码与公共契约统一，不在本模块另起一套状态。缺失采集记录可用于说明覆盖不足，不能变成趋势中的零值。

供 A6 使用的是当前有效证据；供 A5 使用的同时包括可用指标和明确缺失说明。保留必要处理版本，重复处理不重复产生有效修订或变更。

#### 一期与后续

一期完成常见类型、时间、单位、缺失、重复和更正流程，能用固定模拟数据验证。大规模规则回放、复杂任务调度后续扩展；公共处理能力保留可重入接口。

请交付源文件、规则说明、接口调用及实际验证结果，能够与 A2 和后续统计衔接。

#### 验收

- 同一事件重复提交不新增事实，内容冲突能显示。
- 开盒与本人确认各自保留，后续统计不因证据条数增加计划次数。
- 相同时间的不同偏移表达能够正确统一。
- 缺失不填零，未知单位不转成猜测数值。
- 更正后原始依据仍可查，当前输入唯一，不跨患者修改。
- 迟到或更正后能登记受影响结果，程序失败不会被标成患者数据无效。

### A5 动态状态摘要

请汇总 A4 的有效指标、A6 的用药统计，以及 B 和社会支持模块提供的反馈，生成网页和其他模块可以直接读取的近期状态摘要。沿用总约束、公共契约和已有后端代码。

#### 模块目标

读取近期数据 → 整理用药和生理情况 → 标明来源及不足 → 返回摘要 → 数据变化后更新。

摘要帮助其他模块了解患者当前有哪些已知情况，不重新分类画像、预测 CAS 或生成心理诊断。具体干预由 B 决定。

#### 输入

- 患者、授权、查询时间范围及模拟环境。
- A6 返回的计划时段数、本人已服数、本人未服数、暂时延迟数、仅其他证据数、未知或待复核数和确认比例。
- A4 提供的有效指标、实际采样时间、单位及缺失原因。
- B 提供的自评、心理信息或干预反馈；社会支持模块提供的服务状态和患者反馈。
- 各来源更新时间及必要版本。

缺少某一来源时说明未采集或未接入，不把它补成零或假装已有完整评分。患者原话、自评与模型推测保留不同来源，不直接混成一个总分。

#### 汇总逻辑

**1 用药概况**

直接引用 A6 对应窗口的结果，不在摘要里另算一套比例。展示计划完成记录、其他证据与未知情况，并保留统计口径和更新时间。

**2 生理与生活信息**

整理已有的睡眠、活动及生理指标。提供最新有效值、采样时间及足够可比数据支持的数值变化；样本不足时说明暂不能判断趋势。

不同方法或单位的指标不强行合并，不自行定义心理脆弱或认知负荷阈值。生理变化作为 B 的参考输入，不自动生成疾病诊断或用药调整。

**3 干预与支持反馈**

沿用 B 和社会支持模块的记录，整理实际执行状态及反馈。社会支持反馈保留“支持需求变化、支持接受程度、干预效果”三个维度，不凭一次申请认定服务完成或有效。

暂未接入时可用明确标注的模拟数据演示交接；无反馈和接口不可用要分别说明。

**4 数据不足与更新**

逐项说明哪些信息可用、哪些缺失或等待更新。缺少生理指标不影响本来有效的用药统计，不把整名患者标成全部无数据。

新记录、补录、更正或计划变化后，摘要重新计算或明确标为待更新。重复更新不重复产生业务记录，旧结果不能继续假称最新。

#### 输出与网页呈现

返回患者、摘要编号、时间范围、更新时间、数据状态，以及用药概况、指标概况、反馈概况和不足项。字段统一写入公共契约，其他模块直接使用。

网页展示应简短清楚，例如“本周 14 个计划时段，11 个本人确认已服，0 个本人未服，0 个暂时延迟，2 个仅有其他证据，1 个未知；活动数据尚未接入”。同时能查看具体记录和待复核原因，不显示未经依据的健康结论。

B 从同一摘要读取策略所需信息；网页不能自己补齐缺失分数，A 也不重新规定上游画像体系。

#### 一期范围

先支持指定窗口查询、基本汇总、明确缺失和手动更新。可由后续公共任务调用同一更新能力，不另外建立一套算法。

真实可穿戴、复杂多模态评分、自动学习及大规模历史回放后续扩展。是否缓存根据实际需要决定，首次运行不要求单独缓存服务。

#### 验收与交付

- 14 个时段的 10/14 基础结果与 A6 一致，不重复计数；加入未服、延迟或待复核记录后，摘要继续引用 A6 的五类结果，不自行重算。
- 补录一个未知时段后更新为 11/14，摘要的时间和依据相应更新。
- 缺少生理或反馈来源时，保留已知内容并显示不足，不生成假分数。
- 模拟服务仅申请、未完成时，不显示真实支持已完成。
- 患者甲不能读取乙的摘要；模拟和真实数据不混用。

请交付摘要代码、调用和网页数据示例、更新入口及实际验证结果，注明各外部来源是否真实接入。

### A6 用药记录匹配与评价

请将 A4 整理后的有效证据关联到正式用药计划，形成供网页、B 和后续摘要使用的统计与趋势。沿用总约束、公共契约及已有工程，不重复清洗或重新计算画像。

#### 模块目标

确认计划和时段 → 取得有效证据 → 匹配对应时段 → 按时段统计 → 展示趋势 → 补录或更正后更新。

本模块统计的是患者确认及其他证据，不把自报或开盒直接当作已经客观验证的吞服，也不把统计比例当作 CAS 模型预测。

#### 输入

- 当前患者、查询范围及患者时区。
- 正式计划编号、版本、有效区间及稳定计划时段。
- A4 的当前有效记录、来源、质量和发生时间。
- 必要的查询权限、模拟标记和统计规则版本。

先与计划模块统一：时段由谁提供、按每种药的一次计划用药还是合并行为计数、多药同时间怎样处理。未统一时不能在本模块自行决定另一套分母。

#### 匹配逻辑

1. 优先验证已有时段引用，核对患者、计划版本和规定条件。
2. 没有直接引用时，只按团队确认的条目、来源绑定和时间范围寻找候选。
3. 有唯一合法候选时可自动匹配；没有候选或存在多个候选则保留未匹配或需复核原因。
4. 同一时段可关联开盒和本人确认等多条证据；一个原子证据不默认代表所有药物均服用。
5. 不为提高比例强行选择最近时段，匹配和提醒时间也不能改变医嘱安排。

保留匹配依据及必要版本。更正后采用当前有效关联，不让一个已被替代的旧关联继续计数。

#### 统计逻辑

分母来自查询范围内符合约定条件的唯一计划时段，不是上传记录条数。已取消、被替代及未来尚未到时的计划按统一口径处理，不直接当作漏服。

采用以下五类统一口径，与共同接口一致：

| 统计类别 | 含义 | 字段 |
| --- | --- | --- |
| 本人确认已服 | 本人明确报告该时段已经服药。 | `patient_confirmed_count` |
| 本人报告未服 | 本人明确报告该时段未服药。 | `reported_not_taken_count` |
| 暂时延迟 | 本人表示暂时延后，尚无后续结果。 | `postponed_count` |
| 仅有其他证据 | 有开盒、家属报告或设备推断，但无本人明确状态。 | `unconfirmed_evidence_count` |
| 未知或待复核 | 证据不足，或存在尚未解决的冲突；附原因。 | `unknown_count` |

五类按计划时段互斥统计，总数等于纳入统计的计划时段数。证据原文和历史仍分别保存。

患者确认比例＝本人确认已服时段数÷有效计划时段数。明确未服和暂时延迟不计入分子；这一比例仍是本人报告口径，不代表客观验证的吞服率，也不是 CAS 预测值。

延迟后补充明确结果时，更新当前分类，不重复增加计划时段。矛盾证据保留原因并进入待复核，不能静默覆盖或显示为普通“无记录”。

patient_confirmation_ratio＝patient_confirmed_count÷planned_dose_count。分母确为零时比例为空并解释原因；计划服务不可用不能伪装成没有计划。

本人明确未服和暂时延迟分别进入对应类别；没有本人明确状态的家属报告、开盒或设备推断进入仅其他证据。无法由有效记录或更正解决的矛盾进入未知或待复核，并明确原因、保留原始依据。开盒与推断的证据分项可以重叠，不能把分项相加当作总时段数。

跨天汇总先加总分子和分母再求比例，不直接平均每天的百分比。

#### 更新与趋势

补录按实际发生和关联时段归属，不能仅因晚上传判成晚服。时间指标使用来源真正支持的含义；只能获得确认操作时间时，就展示确认时间偏移，不冒充真实吞服时间。

新增有效证据、更正、撤销或计划变化后更新对应结果，保留统计更新时间、计划与计算版本，并通知 A5。旧新窗口都受影响时都要更新，不把旧结果继续标为最新。

一期先支持当前结果和必要版本追踪；完整历史回放、复杂快照系统后续完善，不作为首次跑通统计的前置条件。

提供按日或约定周期的统计，以及实际生理指标趋势。缺失不填零，不伪造每日改善曲线；不同方法或单位的指标不混成一条线。

返回计划时段数、本人确认已服数、本人报告未服数、暂时延迟数、仅其他证据数、未知或待复核数、确认比例、时间范围、更新时间及必要质量说明，并能查看对应记录、冲突依据或未匹配原因。

B 用于支持性对话，A5 用于综合摘要。A 不重复规定患者画像分类，也不据此自动调整治疗方案。网页只展示结果，不自行另算一套比例。

## 6 B AI 沟通、心理信息与干预

本章先以 single_pass 形成可演示闭环，再在 S06 实现受预算约束的 STAR 扩展。真实 API 和模拟模式都通过同一适配；与 A、O、C 复用公共工程与事实。

### B1 模型服务适配

统一接口接收调用标识、消息、预期输出格式、已允许的生成参数及调用预算；返回状态、内容、来源、模型、错误、用量、耗时和尝试次数。

实现可配置的 OpenAI 兼容聊天 API 与确定性模拟适配，供应商暂不锁定。后续心理领域模型必须通过同一接口接入，不能重写业务层。心理专用模型的自部署、微调和模型质量比较不作为本期默认必做任务。

- 密钥、地址、模型和生成参数由后端配置，患者消息或网页请求不能任意覆盖。
- 参数兼容性集中处理；不向不支持的服务强传 JSON 或采样参数。
- 文本与 JSON 的语法、空响应、截断、超时和限流都要处理，禁止 `eval`。
- 每轮固定配置快照，异步调用或等价方式避免阻塞服务；模型调用期间不持有长事务写锁。
- 重试有次数和总时间预算，鉴权、配置及不支持参数不重试。真实失败不静默降为模拟成功。
- 单次对话预算由编排层统一分配，底层重试计入同一预算，不能各子模块分别无限消耗。
- 模拟正常、超时、空响应、格式错、知识不足和分步中途失败；所有测试默认无付费调用。
- 日志保存必要元数据；完整对话仅进入受控的业务记录，不默认复制到控制台日志。不要保存模型推理链。

预期：业务模块独立于供应商和部署方式；密钥缺失时仍可运行模拟闭环；真实连通性和各参数能力未经探测时明确标注未验证。健康查询不付费，显式模型探测说明会产生外部调用。

### B2 审核知识检索与来源

B2 维护平台共用的知识资料、审核状态、来源版本和检索能力，供药学知识页面、B3 对话及社会支持页面复用。资料解释不等于药师咨询答复，不能将 LLM 生成内容标记为专业人员意见。演示阶段可共用少量本地示例资料，无须因此增加复杂知识库建设；未审核材料必须如实标识。

#### 知识记录

每条材料至少有 ID、标题、正文、来源定位、适用范围、语言、版本、审核状态、生效时间及可选失效时间。审核状态区分草稿、待审核、已审核、已撤回。

只有适用且有效的已审核内容可以作为医学事实或专业支持依据。示例材料没有真实审核时明确标识，不伪造审核人、机构、日期或权威性。项目组未提供材料时，用少量通用沟通原则运行，并将医学检索返回知识不足。

#### 检索工作流

对话需求和适用信息 → 过滤状态、版本与范围 → 检索 → 返回片段及来源 ID → 在模型生成中限定可用依据 → 校验引用确实来自本次返回集合。

先完成小规模关键词/标签检索，保证可追溯；向量检索与重排作为独立可替换适配，只有实际规模需要时再引入。纯共情无需为了展示而强行引用知识。

知识不足或冲突时明确说明局限；不能补造药学结论，必要时产生专业支持建议。撤回材料不得再检索，旧会话引用仍能查看当时版本和后续状态。

材料内容不作为系统指令，不允许改变权限或诱导工具执行。读到外部 URL 不代表已经核实其中所有结论。

预期：用少量资料证明检索过滤、版本追溯、撤回、无结果、引用校验及资料中的提示注入处理。知识内容由项目组确认，开发 AI 不以模型自评冒充专业审核。

### B3 支持对话与 CAMI 式编排

#### 通用沟通原则

身份为 AI 支持助手。先理解并回应具体困扰，再按意愿探索用药困难；用户明确请求办法时简短共情后直接给一个低负担选项。用户只想倾诉时允许停留在倾听，拒绝或结束时尊重选择。

以反映、肯定、开放式问题、自主支持、征询许可后的建议及总结为主要策略。每轮通常一个重点，最多一个主要问题，避免重复追问、恐吓、指责、机械共情和长篇说教。不要把精力不足或拒绝等同于抵触，也不强制达成服药承诺。

#### 输入

患者与会话、当前消息、近期历史、画像与经确认计划的必要部分、A 摘要、用户偏好、入口来源、知识片段、既往建议响应和真实应用模式。提供给模型前按用途最小化数据，缺失保持未知。

历史窗口可配置，若增加会话摘要，摘要须有来源消息范围和版本，不能覆盖用户原话。历史摘要也是非诊断性派生信息。

#### 两种对话执行模式

1. `single_pass`：在一次调用中生成回复和结构化信息，作为可运行基线；最多两次网络尝试，含首次和一次暂时性重试。
2. `star`：采用 CAMI 式的分步状态推断、话题探索、MI 策略选择、候选回复及选择。先实现明确的调用预算、失败路径和模拟测试，再接通真实模型。

`star` 的建议默认预算为最多八次网络尝试，包括所有子步骤和重试；该数字是可配置的工程上限，不是疗效参数。限制候选数量和总耗时，超预算返回明确的降阶/失败状态。若预先配置允许降为 `single_pass`，也须在剩余预算内且记录 `requested_pipeline/actual_pipeline/fallback_reason`，不切换成未标识的模拟内容。

#### STAR 场景适配

- 状态推断：改变准备程度与情绪线索分开记录，允许未知。准备程度可以覆盖尚未考虑、存在矛盾、准备行动及已在行动/维持；后两类属于本项目扩展，不能声称全是原 CAMI 实现。
- 话题探索：围绕用户自己的目标、用药顾虑、生活障碍、支持资源和负担。话题结构独立配置，允许用户改变话题或拒绝探索。
- 策略选择：每轮一至两项 MI 沟通策略，允许快速行动支持，不强制走完全部阶段。
- 回复生成：候选回复数量有上限，评价关注具体共情、自主支持、上下文一致和事实边界，避免把顺从或立刻服药当成唯一成功。
- 候选选择记录最终策略、版本及简短业务说明，不存储或展示模型内部推理链。
- CAMI 仓库的主题条目、Wikipedia 内容和参数不能直接作为药学审核知识或本项目临床阈值。
- 不直接把 `generate.py` 的双方模拟循环作为真实会话服务；患者消息来自前端，咨询逻辑逐轮执行。
- 原方法、复用代码与本项目改动分别记录。直接复制代码前核对许可；授权不明确时独立实现公开方法，不自动假设可任意复用。

#### 统一业务输出

保持单轮与分步模式输出兼容：

```json
{
  "assistant_reply": "患者可见回复",
  "support_focus": "listening",
  "difficulty_cues": [],
  "communication_strategy": ["reflection"],
  "suggested_action": null,
  "knowledge_citations": [],
  "change_readiness": null
}
```

`support_focus` 为 `listening/clarifying/exploring/action_support/closing`。策略枚举为 `reflection/affirmation/open_question/autonomy_support/permission_based_advice/summary`。

线索每项含 `category/label/evidence/source_message_id`。建议为 `null` 或包含 `type/description` 的对象，类型为 `small_step/offer_simplified_mode/offer_professional_support`。

知识引用只允许来自当前检索集合，附可定位材料和版本。改变准备程度为未知或带证据的受限枚举；后端而非模型附加真实来源、模型、版本和时间。

校验业务字段。辅助线索单项无依据时丢弃该条并说明降阶；核心回复结构非法时明确失败，不任意抽取原始文本伪装成功。

预期：两种模式可用同一会话 API；不同案例/患者隔离；快速求助、仅倾诉、拒绝、话题转换、知识不足与紧迫危险有可验证路径；输出不可越权执行应用操作。

### B4 心理信息与多源状态融合

#### 四类线索与证据

固定 `low_mood` 情绪低落、`anxiety_concerns` 焦虑与担忧、`treatment_fatigue` 治疗倦怠、`routine_barriers` 生活与执行困难。允许多个及空列表。

模型线索引用当前会话真实用户消息及原文；后台核对消息归属和本次输入范围。不得引用助手消息，不能以用户拒绝为分类依据。历史线索标明时间，不永久累加成当前状态。

患者原话、自评记录、模型推测和 A 的设备/行为指标分别保存、分别展示。生理或行为信号只作为上下文证据，不单独认定为心理疾病。

#### 评估记录与融合

顾虑、必要性感知、负担分别定义条目、量程、评分方法、缺失规则及版本。没有确认的方法时使用描述性记录，不编造总分。使用量表须核对适用条件和使用要求，不能由模型临时生成“标准量表”。

同方法同量程才能直接比较趋势，方法变更标明边界；跨来源不随意相加。更新摘要包含来源、观察窗口、时效、覆盖情况、不足项和证据引用。保存融合规则版本，不把不确定性说明伪装成已校准概率。

评估节点以服务启用 `enrollment_at` 为默认起点，第 1、4 周的日偏移和触发窗口可配置。计划更新默认不重置周期，如研究要求不同必须显式配置。数据不足时询问、请求更多信息或标明不足，不补零。

B4 默认复用 B3 及 A 的现有输出，不重复调用模型；新增评估调用必须纳入统一预算和明确阶段范围。

预期：原话、自评和推测可区分；跨患者及虚构引用被拒；过期和缺失被保留；评分/方法版本能追溯，未定义时不会生成看似精确的分数。

### B5 干预规则与执行协调

#### 决策维度

以可配置规则为主，输出是否干预、支持类型、支持强度、交互负担、渠道建议、时点、理由与有效期。保留暂不干预。阈值和连续观察窗口必须有定义、版本及用途说明，演示阈值明确标记，不能称为临床有效阈值。

LLM 可以提出沟通策略和候选建议；应用规则检查用户偏好、证据有效性、频率限制、实际状态和权限后，才生成可执行操作。不要让 LLM 直接触发推送、改药或修改授权。

支持强度与负担分开：更多支持可以对应更少任务。一次无记录、一次开盒或一个心理词不直接触发家属警报或心理风险升级。

#### 极简模式

`normal` 展示聊天、核心用药确认、可选任务和科普；`simplified` 隐藏非核心任务及科普推送，保留聊天、核心用药确认及恢复按钮。隐藏不删除、不改计划；两种模式均保留全局导航、积分权益和主动申请社会支持的入口。

本扩展阶段仍以明确用户操作作为首次进入极简模式的默认条件。以后若需要自动切换，必须另行确定授权与研究规则，本 Prompt 不擅自启用。配置模式有效期、最短维持时间、再次建议间隔和恢复条件；期限恢复应有记录和可见说明。

本地模式默认会话级；对接小程序时，如需患者级跨会话生效，作为显式范围配置并迁移，不暗中改变语义。

建议状态为 `pending/accepted/declined/cancelled/expired`。相同待响应建议去重；拒绝后不在同轮反复建议；新的明确请求可以重新生成。相反响应不覆盖历史。重复选择当前模式不产生变更事件。

#### 三类入口与调度

用户主动、定期评估、状态事件。后两者生成邀请，用户接受后才开始沟通，不代替用户写消息。邀请状态为 `pending/accepted/declined/expired/cancelled`，展示时间单独保存。

B 定义业务触发条件；A/公共系统统一负责任务执行和投递。B 独立测试使用隔离的任务适配和可控时钟，集成时复用公共任务能力，不并行启动另一套调度；不能依赖网页一直打开，也不能在每次启动重复创建检查。

按患者、事件/评估节点和规则版本明确去重语义。规则版本更新不默认重新骚扰已完成节点。迟到数据可重算摘要与候选策略，但不得重复执行已有干预；保留重算与取消原因。

#### 决策与执行状态

决策、投递、展示、响应分别记录。执行状态至少包括待执行、已提交、已送达、失败、取消和过期；不支持送达回执时保持未确认，提交不等于送达。

B 提供策略和响应 API，A 的渠道适配执行投递并回传；本地模拟渠道标明来源。授权、偏好或会话状态变化后，待执行操作重新校验。重复回调不得重复计数，回调乱序按明确状态规则处理。

**与社会支持模块的衔接约定**

1. **B 负责发现和表达支持需求。** 通过对话及状态信息，提出药师咨询、情感陪伴或实际生活协助等建议，并说明依据。

2. **社会支持模块负责具体服务匹配。** 综合阶段2画像、动态信息、B 提供的需求、患者意愿、授权和资源情况，匹配家人、志愿者或药师。患者也可以直接进入社会支持页面申请，无须先经过 B 对话。

3. **实际服务申请统一由社会支持模块创建。** 患者确认服务及必要的信息共享范围后，生成唯一服务记录。B 通过该入口衔接，保存来源建议与返回的服务记录标识，不另建一份实际申请。B 接口如保留转介入口，应复用这一创建能力。

4. **服务执行状态以社会支持模块的记录为准。** B 和 A 读取或接收状态回传，用于沟通、汇总及评价；不能仅凭建议被接受就认定服务已经受理或完成。

5. **已完成的确认应复用。** 同一服务及相同信息共享范围已经取得有效确认时，不重复询问；服务主体或共享范围发生变化时，再取得对应确认。

撤销授权或取消后的晚到回执保留审计，不自动恢复操作。

预期：任一决策可以追溯输入及规则；过期证据、重复触发、服务重启、撤销授权、乱序回执和未完成转介均有明确行为；前端展示实际执行状态。

### B6 业务记录与研究反馈

#### 保存与查询

定义患者/案例引用、会话、消息、知识版本引用、评估、触发事件、邀请、建议、干预决策、执行、用户响应、模式变更、转介、任务运行及模型调用记录之间的关系。

复用 A 统筹的公共数据库和迁移；B 的独立测试使用隔离 SQLite 测试库。外部模型调用与业务事务边界清楚，防止长锁、重复付费和部分写入。记录成功前不返回已执行成功。

提供分页的会话历史、单次决策详情、按时间范围的干预/响应导出及 A 所需反馈查询，限制字段和访问范围。导出中明确模拟/真实来源、方法版本和数据缺失。

反馈先更新状态与下一轮策略。模型训练和微调不在业务请求中进行，不自动拿患者对话训练。

#### 演示管理

预置情绪低落、焦虑与用药顾虑、长期用药倦怠三个虚构案例；允许自由输入。开场只填草稿，真实模式现场生成回复。支持模型、流水线、知识无结果、事件和回调的模拟检查，避免模拟 ID 引用到其他会话。

新会话默认普通模式，案例切换清除网页旧状态。历史建议只读。

按当前案例确认后重置业务记录，保留模板、其他案例及模型配置；事务失败回滚。真实环境禁用演示重置和伪造事件入口，不允许无授权操作真实患者。

#### 身份与集成模式

明确区分 `demo` 与 `external` 身份模式。本地虚构案例可使用固定演示身份；这不代表实现了真实认证。

外部身份、授权和设备回调分别有可替换适配及契约。`external` 模式依赖未配置时拒绝启动或拒绝相关操作，不能静默退回演示身份。实际接入使用团队约定的身份及签名验证，不自行发明生产授权协议。

预期：重启持久化、对象级隔离、事务回滚、按范围重置、受限查询和来源可追溯；不把技术流程或趋势当成干预因果效果。

## 7 C 社会支持、积分与服务反馈

本章是平台内的社会支持业务，不是独立智能体或另一套网站。服务执行可以模拟，但申请、状态、积分和反馈必须经过统一后端并持久化。

### C1 模块定位

本模块是药物依从性监测与干预大模型中的一个功能模块，隶属于阶段3：个性化策略实施环节，不是独立运行的智能体。

模块直接接收阶段2已经形成的患者用户画像（药物依从性分类），结合患者当前的动态用药信息、生活情境及支持意愿，判断患者是否需要外部社会支持，并匹配相应的支持主体与干预策略。

平台业务协调层是同一 Python 后端中的普通业务调用逻辑，负责按约定连接画像、数据、B 和社会支持模块，不新增一个独立大模型。阶段2画像由 O 模块维护；A 汇总记录与反馈；B 提供对话支持和需求建议；社会支持模块维护服务匹配、申请及执行状态。

本模块设置三类社会支持主体：

1. **志愿者**：提供同伴支持、情感陪伴及必要的社区协助。
2. **家人**：提供药品获取、取药、续方、辅助配送及日常情感支持。
3. **医院药师**：提供专业药学咨询、用药指导及专业问题转介。

同时设置激励机制，通过匿名同辈支持微小组和积分兑换私人定制化服务，增强患者参与疾病管理的积极性。

核心目标是将社会支持融入个性化药物依从性干预过程，帮助患者克服长期用药中的社会性、心理性和实际操作性障碍。

**产品设计原则：社会支持根据患者需求动态触发，积分权益作为长期存在的独立功能，两者相互关联但不相互依赖。**

### C2 输入与数据来源

本模块不重新采集和计算阶段2已经处理的数据，而是直接调用阶段2输出的患者画像。

#### 阶段2用户画像（主要输入）

接收阶段2画像模块提供的以下信息：

- 患者药物依从性分类；
- 患者所属的依从性问题类型；
- 患者相关的基础画像信息；
- 已有的依从性评价结果。

患者分类沿用既定体系：

**（1）高依从性患者：** 采用维持型干预。

**（2）低依从性患者：**

- 无意不依从：遗忘与习惯缺失型、操作与外部条件受限型。
- 有意不依从：用药认知不足型、用药顾虑与心理抗拒型、情绪低落与用药疲劳型。
- 有意与无意因素兼有：社会情境与生活冲突型。

患者可以同时存在多个障碍。社会支持模块应直接引用阶段2提供的主要类型、其他相关障碍及支持需求，不能仅因患者存在某项顾虑就重新判定其为低依从性患者。

本模块不重新进行依从性判定，不重新计算 CAS，也不自行改变阶段2的分类结果。

#### 阶段1及阶段3运行过程中可调用的动态信息

根据系统实际接入情况，调用以下信息：

- 病历单及药物使用信息；
- A 汇总的用药状态：本人确认已服、本人报告未服、暂时延迟、仅有其他证据、未知或待复核；智能药盒开盒等仅作为对应证据来源；
- 药品库存及补充情况（有相应数据时）；
- 可穿戴设备（如有）提供的生理及生活方式信息；
- 患者主动提供的用药困难和心理反馈；
- 已授权的家庭支持信息及外部支持参与情况。

上述信息用于判断患者当前是否存在需要外部协助的实际情况，不用于重新生成依从性分类。

用药记录、五类计数和患者确认比例统一读取 A 的结果；本人未服与暂时延迟不计入已服分子，确认比例不等于客观吞服率或 CAS。未知或待复核时保留原因，不能据此直接认定漏服；本模块不自行重算比例。

#### 权限与隐私信息

调用患者及家庭账号的授权状态，需明确：

- 患者是否允许家人获取相关信息；
- 患者是否愿意接受志愿者支持；
- 患者是否同意联系医院药师；
- 各支持主体能够获取的信息范围。

不得向未经授权的第三方共享患者信息。相关授权最好在阶段1数据采集及账号设置时共同明确。

### C3 支持主体匹配与 B 衔接

根据阶段2已经形成的患者画像，结合当前动态信息和患者意愿，匹配适当的社会支持主体。

**与 B 模块的衔接约定**

1. **B 负责发现和表达支持需求。** 通过对话及状态信息，提出药师咨询、情感陪伴或实际生活协助等建议，并说明依据。

2. **社会支持模块负责具体服务匹配。** 综合阶段2画像、动态信息、B 提供的需求、患者意愿、授权和资源情况，匹配家人、志愿者或药师。患者也可以直接进入社会支持页面申请，无须先经过 B 对话。

3. **实际服务申请统一由社会支持模块创建。** 患者确认服务及必要的信息共享范围后，生成唯一服务记录。B 通过该入口衔接，保存来源建议与返回的服务记录标识，不另建一份实际申请。B 接口如保留转介入口，应复用这一创建能力。

4. **服务执行状态以社会支持模块的记录为准。** B 和 A 读取或接收状态回传，用于沟通、汇总及评价；不能仅凭建议被接受就认定服务已经受理或完成。

5. **已完成的确认应复用。** 同一服务及相同信息共享范围已经取得有效确认时，不重复询问；服务主体或共享范围发生变化时，再取得对应确认。

#### 志愿者支持

主要针对存在社会支持不足、孤独感、病耻感、长期服药疲劳或缺乏同伴鼓励的患者。

**（1）匿名同伴支持**

针对害怕给家人造成负担（Burdening
Family）或独居的患者，在保护个人隐私和患者自愿参与的前提下，按照以下标签匹配匿名同辈支持微小组：

- 同病种；
- 同用药阶段；
- 相似作息。

通过线上交流、经验分享和相互鼓励，帮助患者建立疾病认同，缓解病耻感和社会孤立感。

**（2）情感陪伴**

通过定期问候、交流和正向鼓励，为缺乏社会支持的患者提供必要的情感陪伴。

**（3）社区协助**

针对独居、行动不便或缺乏家庭协助的患者，在医院或社区服务体系协调下，提供必要的取药、配送等协助。

注意：志愿者不承担专业医疗咨询、药物调整及强制服药监督职责。

#### 家庭支持

家庭支持分为药品获取支持和自主支持。

**（1）药品获取支持（Obtaining Medication）**

- 根据智能药盒库存、实际服药记录和医嘱用量，判断药品是否即将耗尽。
- 在患者授权后，向家属端推送药品补充协助请求。
- 提供线上续方、取药及配送服务入口。
- 如果家属无法提供协助，则考虑转向医院药师或社区服务资源。
- 将药品获取状态提供给 A 汇总，并供 B 在权限范围内读取。

**（2）自主支持（Autonomy Support）**

当系统发现患者存在持续性漏服趋势，且伴随心理脆弱或生活管理困难时，在患者授权范围内向家属提供温和提示。

根据患者当前的问题，为家属生成非指责性的沟通建议，引导家属从监督服药转向生活协助、情感关怀和积极鼓励。

例如：

- 不建议："患者已经连续几天没有吃药，请立即督促。"
- 建议："最近可以多关心一下患者的日常状态，了解是否遇到了用药或生活方面的困难，询问是否需要帮助。"

**（3）智能风险过滤**

- 单次或偶发性漏服不直接触发家属警报。
- 仅在持续性漏服趋势或相关心理脆弱信号出现时，考虑启动家庭支持。
- 所有信息共享必须符合患者授权范围。
- 不得将家属默认设定为患者的服药监督者。

#### 医院药师专业支持

主要针对用药认知不足型、用药顾虑与心理抗拒型，以及存在其他专业药学问题的患者。

**（1）药学咨询**

本模块负责药师咨询的申请、授权、服务进度及专业答复展示。申请前的知识说明可复用 B2 的适用资料，不独立维护另一套知识库。

**（2）药物顾虑处理**

承接患者主动提出或 B 模块建议进一步咨询的专业问题，在患者确认和授权后建立服务申请，由药师提供专业评估与答复。未接入真实药师时，明确标注模拟申请、模拟状态或示例答复，不将 AI 回复显示为药师已经作出的答复。

**（3）用药风险转介**

当患者反映疑似药物不良反应、药物相互作用或其他专业问题时：

- 收集患者主动提供的相关信息；
- 识别是否存在需要及时就医的风险；
- 在患者授权后，将相关问题转交医院药师；
- 由药师进一步评估，必要时联系医生。

**（4）药学随访**

对于存在持续性用药顾虑或专业药学支持需求的患者，提供适当的随访建议。

**（5）专业反馈**

将药师咨询结果、患者问题解决情况及后续建议提供给 A 汇总，并供 B 在权限范围内读取，为后续个性化干预提供依据。

注意：AI不得代替药师或医生进行诊断、处方、停药或药物剂量调整。

### C4 激励、积分与兑换

激励机制作为社会支持模块中的辅助功能，主要通过社会认同和正向行为强化，提高患者参与疾病管理的积极性。

**本期积分实现口径**

本期采用正向奖励与自愿兑换：依据有效记录和健康管理参与行为发放积分，用户自主选择是否兑换权益。不因漏服、身体不适或遵医嘱暂停用药而扣除已有积分，不奖励超出医嘱的服药行为。

积分由后端按照明确规则计算。必要的医疗诊疗及专业药学咨询不以积分为前置条件。

原功能设计中的家庭共同账户、预充健康津贴和损失厌恶扣减契约不纳入本期实现，作为后续可选方案另行设计；编码时不得自动补充家庭连带扣分或监督惩罚机制。

设置以下两种形式。

#### 匿名同辈支持微小组

**（1）匹配机制**

针对害怕给家人造成负担（Burdening
Family）、独居或存在社会支持不足的患者，在患者自愿参与和隐私授权的前提下，根据以下标签进行匹配：

- 同病种；
- 同用药阶段；
- 相似作息。

**（2）系统呈现**

平台业务协调层依据阶段2画像和可用动态信息（包括 A 的状态摘要及 B 提供的支持需求），调用社会支持模块。社会支持模块匹配并确认存在相应需求时，在小程序首页动态推荐区域生成同伴支持推荐卡片。

卡片展示：

- 推荐加入的原因；
- 匿名同伴小组简介；
- 小组交流主题；
- 加入及暂不参与选项。

患者确认后进入匿名交流小组，可进行经验分享、相互鼓励和主题交流。

**（3）运行机制**

- 患者自主决定是否加入及退出；
- 不向其他成员展示真实身份和未经授权的疾病、用药信息；
- 志愿者负责必要的交流引导；
- 不允许将同伴交流替代专业医疗咨询。

#### 积分激励与私人定制化服务（健康成长权益）

积分权益是长期存在的独立功能，不随社会支持需求的变化而隐藏或关闭。

通过记录患者实际的服药打卡行为和药物依从性管理参与情况，建立健康积分体系。

**（1）积分获取规则**

建议采用以下初步规则：

| 积分行为 | 建议积分 | 规则 |
| --- | --- | --- |
| 完成当日有效用药记录 | +2 | 每日最多一次 |
| 连续5天完成有效记录 | +5 | 阶段性奖励 |
| 完成每周用药管理回顾 | +3 | 每周一次 |
| 参与匿名同辈支持活动 | +2 | 每周最多一次 |

积分规则可以根据实际测试情况进行调整。

积分机制遵循以下原则：

- 不因漏服、身体不适或医生要求暂停用药而扣除已有积分；
- 不奖励超出医嘱的服药行为；
- 以有效记录和健康管理参与行为作为积分依据；
- 避免因患者原有依从性水平不同而造成不合理的奖励差异；
- 积分应由程序根据有效记录和既定规则核算，不由大模型自行决定或直接修改账户余额。

**（2）积分兑换服务**

在小程序中设置独立的「积分权益」入口，患者可以随时查看当前积分、积分获取规则及可兑换服务。

建议设置以下兑换项目：

| 服务类别 | 具体内容 | 建议积分 |
| --- | --- | --- |
| 专属提醒定制 | 提醒方式、界面主题、音效定制 | 30 |
| 个人用药管理卡 | 生成可保存的用药记录及注意事项卡片 | 40 |
| 个性化作息计划 | 根据现有作息生成日常管理清单 | 50 |
| 志愿者陪伴服务 | 预约一次线上问候或陪伴交流 | 60 |
| 健康管理工具包 | 获取个性化打卡表、用药整理清单等 | 80 |

以上积分为初步产品设计参数，后续根据服务成本、资源供给及用户测试结果调整。

医疗诊疗、必要的专业药学咨询不得设置为积分兑换的前置条件。

**（3）兑换与服务交付**

患者选择服务并确认兑换后：

1. 系统检查积分是否充足；
2. 扣除对应积分并生成兑换记录；
3. 根据服务类型自动生成数字化内容，或创建相应的志愿者服务预约；
4. 服务完成后收集患者评价。

**（4）兑换记录**

积分权益页面设置独立的兑换记录入口，记录：

- 已兑换的服务名称；
- 兑换所消耗的积分；
- 兑换时间；
- 服务交付状态。

兑换记录与社会支持服务记录分别管理。

**（5）反馈机制**

将患者积分获取、兑换及服务参与情况提供给 A 汇总，并供 B 在权限范围内读取，用于分析激励措施的参与程度和实际效果。

### C5 支持决策与强度

根据阶段2的患者画像，结合当前动态信息和患者意愿，决定是否启动相应的社会支持。

决策时遵循以下原则：

1. 高依从性患者：以维持型支持为主，不主动进行不必要的第三方干预。
2. 遗忘与习惯缺失型：优先考虑必要的家庭日常协助。
3. 操作与外部条件受限型：优先考虑家人取药、续方及社区志愿者协助。
4. 用药认知不足型：优先匹配医院药师专业支持。
5. 用药顾虑与心理抗拒型：优先匹配医院药师，必要时结合家人提供非指责性支持。
6. 情绪低落与用药疲劳型：优先考虑志愿者同伴支持及家人情感关怀。
7. 社会情境与生活冲突型：根据患者实际需求，考虑匿名同辈支持、家人协助及社区资源。

对于同时存在多种障碍的患者，可以组合调用多个支持主体。

以上匹配属于初步策略，实际执行还需要考虑患者的支持意愿、授权情况及资源可用性。

对于不需要外部支持的患者，维持原有个性化管理策略。

对于疑似严重药物不良反应或紧急医疗风险，优先进行医疗安全转介。

### C6 反馈与自适应

社会支持模块保留三个反馈维度，并将反馈结果提供给 A 汇总，供阶段4进行效果评价，并供 B 在权限范围内读取以支持后续策略调整。

#### 支持需求变化（Support Needs）

收集：

- 患者原有的社会支持需求是否仍然存在；
- 原有用药障碍是否得到缓解；
- 是否出现新的社会、心理或实际生活困难；
- 患者是否需要更换支持主体。

目的：动态了解患者支持需求的变化。

#### 支持接受程度（Support Acceptance）

收集：

- 患者是否愿意接受本次支持；
- 患者是否主动参与相关支持活动；
- 患者对家人、志愿者或药师支持的主观感受；
- 患者是否希望减少、增加或更换支持方式。

目的：判断当前支持策略是否符合患者意愿，避免过度干预。

#### 干预效果（Intervention Effectiveness）

收集：

- 家人是否成功协助完成取药或药品补充；
- 志愿者支持后患者的主观感受是否改善；
- 药师咨询后患者的相关用药问题是否得到解决；
- 后续服药记录及依从性评价指标是否发生变化；
- 匿名同辈支持及积分激励的参与情况。

目的：评价不同支持方式是否有效。

#### 反馈应用

将三个维度的反馈信息提供给 A 汇总，并供 B 在权限范围内读取：

- 若支持需求持续存在且患者愿意接受，则维持或调整原有支持方式；
- 若支持需求已经缓解，则适当降低外部支持强度；
- 若患者不愿意接受当前支持，则考虑调整支持主体或方式；
- 若原有支持方式未能解决问题，则重新匹配其他支持资源。

阶段4汇总长期反馈及依从性变化，为评价和策略调整提供依据。画像更新由阶段2画像模块按已确定的评估规则完成；其他模块不直接覆盖画像，也不因收到反馈就自动修改模型参数。

注意：一次服务申请不等于干预完成，只有获得实际服务执行结果及患者反馈后，才能评价干预效果。

### C7 页面与执行机制

本模块的社会支持服务和积分权益分别设置独立入口，同时通过平台业务协调层和后台数据进行关联。

本模块提供首页的社会支持推荐、支持服务中的社会支持页面、积分权益及“我的”中的服务记录与授权入口。用药管理和 AI 情感支持复用相应模块页面，不在本模块重复开发。

#### 首页（Home）

首页作为患者日常使用的主要界面，主要展示：

- 今日用药管理及记录情况；
- 当前主要的健康管理信息；
- 根据患者画像和动态需求生成的社会支持推荐卡片；
- 当前积分余额的简要展示；
- 最近服务状态及快捷入口。

社会支持卡片采用情境触发方式：

- 药品获取困难：展示药品补充与家人协助卡片；
- 社会支持不足：展示匿名同辈支持卡片；
- 用药专业问题：展示医院药师咨询卡片；
- 其他明确支持需求：展示相应的服务入口。

原则上优先展示一个当前最需要的支持行动。存在多个重要需求时，可以提供次要支持入口，避免同时推送大量信息。

当患者当前不需要外部支持时，不额外生成干预卡片，维持原有用药管理流程。

#### 支持服务中的社会支持（Social Support）

在“支持服务”下设置独立的“社会支持”二级页面，集中展示当前可用的外部支持服务；与“AI 情感支持”二级入口分别呈现。

根据患者当前需求，展示相应的服务入口：

- 志愿者支持；
- 家人取药及生活协助；
- 医院药师专业咨询。

不需要向每位患者展示全部服务，优先呈现当前与患者画像及实际需求相匹配的服务。

患者点击对应服务后，进入简化操作流程：

- 家庭支持：确认是否向家人发送协助请求，并完成必要授权；
- 志愿者支持：查看匹配信息并申请加入；
- 医院药师支持：提交咨询问题并申请专业服务。

所有涉及第三方信息共享和服务申请的操作，均需获得患者确认及相应授权。

#### 积分权益（Health Rewards）

积分权益是长期存在的独立功能，不随社会支持需求的变化而隐藏或关闭。

主要展示：

- 当前可用积分；
- 积分获取规则；
- 可兑换的私人定制化服务；
- 服务兑换入口；
- 历史积分获取及消费记录；
- 历史兑换服务及交付状态。

患者可以自主浏览和兑换服务，不需要等待社会支持模块触发。

#### 我的（Profile）

主要展示患者个人信息、授权管理和历史服务记录。

其中设置独立的「服务记录」入口，集中记录患者通过社会支持模块发起的所有服务申请。

服务记录包括：

- 家人取药、续方及配送协助；
- 志愿者陪伴、社区协助及匿名小组申请；
- 医院药师咨询与随访申请；
- 其他社会支持服务。

每条服务记录应展示：

- 服务名称；
- 服务主体；
- 申请时间；
- 当前执行状态；
- 相关服务说明。

申请准备与正式服务记录分别管理：

- **待确认草稿**：患者尚未完成必要确认或授权，不属于已提交的服务申请，不通知服务方。

完成必要确认与授权并正式提交后，创建唯一服务记录，其执行状态分为：

1. **已申请 `submitted`**：已完成必要确认与授权，正式提交，等待服务方受理。
2. **进行中 `in_progress`**：服务方已受理，正在执行。
3. **已完成 `completed`**：服务方确认完成；患者评价另行记录。
4. **已取消 `cancelled`**：申请被取消。
5. **未能完成 `failed`**：服务无法提供或执行失败，保留原因。

服务状态必须根据真实操作和服务方反馈进行更新，不得仅凭AI生成的建议认定服务已经执行。

积分兑换记录在积分权益页面独立管理，不与社会支持服务记录混合。

#### 服务执行与反馈回传

患者提交服务申请后，系统生成对应的服务记录，并将服务状态提供给 A 汇总，并供 B 在权限范围内读取。

服务执行过程中：

- 患者可以查看服务进度；
- 服务主体可以根据权限反馈受理和执行情况；
- 服务完成后，系统收集患者对本次服务的评价。

将实际服务状态、患者反馈和干预结果提供给 A 汇总，用于阶段4的效果评价，并供 B 在权限范围内读取。

### C8 结构化业务输出

社会支持模块不输出冗长的患者分析报告，而是输出供平台业务协调层和小程序调用的精简行动指令。

每次调用按照以下结构输出：

#### 当前支持状态

- 是否需要社会支持：是 / 否；
- 当前主要支持需求：实际生活支持 / 社会情感支持 / 专业药学支持 /
    暂无；
- 对应患者画像：直接引用阶段2的分类。

#### 当前支持行动

- 支持主体：志愿者 / 家人 / 医院药师 / 多主体协同；
- 行动类型：取药协助 / 同伴匹配 / 情感关怀 / 药学咨询 / 其他；
- 推荐原因：简要说明；
- 执行方式：系统需要提供的具体服务。

#### 交互指令

- 是否生成首页支持卡片；
- 卡片标题及展示内容；
- 卡片对应的社会支持页面入口；
- 患者可执行的操作；
- 是否需要患者授权；
- 点击后调用的服务入口。

#### 激励指令

仅在涉及积分或同辈支持时输出：

- 是否触发积分奖励；
- 应增加的积分及对应规则；
- 是否推荐匿名同辈支持微小组；
- 是否存在适合推荐的积分兑换服务。

积分权益的常规展示、浏览和兑换不需要社会支持模块每次重复生成指令，由积分权益页面独立完成。

#### 服务记录指令

当患者提交社会支持申请后，生成相应的服务记录信息：

- 服务名称；
- 服务主体；
- 申请时间；
- 初始执行状态；
- 需要获得的后续服务反馈。

服务状态由实际执行过程更新，不得由模型自行虚构。

#### 反馈记录

在获得实际反馈后，向 A 提供以下信息以供汇总，并供 B 在权限范围内读取：

- 支持需求变化；
- 支持接受程度；
- 干预执行结果；
- 是否需要继续支持或调整策略。

如果当前不需要社会支持，则仅返回当前无需启动外部支持的状态，不生成多余的支持卡片和干预内容。

如果相关信息不足，则标记待确认，不得自动联系第三方或虚构服务执行结果。

### C9 运行原则

1. 直接沿用阶段2形成的患者画像，不重复计算依从性指数或进行患者分类。
2. 以患者实际用药障碍为依据，而非单纯以漏服记录为依据。
3. 根据患者需求动态匹配社会支持主体。
4. 志愿者、家人和医院药师各司其职，不相互替代。
5. 激励机制以正向强化为主，不增加患者心理负担。
6. 社会支持与积分权益分开管理，前者根据需求动态触发，后者长期开放。
7. 所有第三方信息共享必须经过患者授权。
8. 专业医疗问题由有资质的医疗人员处理。
9. 服务申请、服务执行和服务完成必须严格区分。
10. 通过支持需求变化、支持接受程度和干预效果三个维度持续反馈，优化社会支持策略。

### C10 原型与正式接入边界

当前阶段的目标是完成统一后端支持的可交互网页原型，业务记录持久化到 SQLite；不要求真实接入外部服务。

请明确区分以下内容：

| 功能 | 当前网页原型 | 后续正式系统 |
| --- | --- | --- |
| 患者画像 | 手动切换模拟画像 | 接收阶段2模型输出 |
| 支持策略 | 根据模拟画像动态展示 | 平台业务协调层调用社会支持模块 |
| 家人协助 | 模拟提交申请 | 家属端真实接收及反馈 |
| 志愿者服务 | 模拟申请及状态变化 | 志愿者端受理和执行 |
| 药师咨询 | 模拟提交咨询 | 医院药师端接收和回复 |
| 积分计算 | 后端按演示规则计算 | 后端依据有效记录计算 |
| 积分兑换 | 后端扣分及数据库记录 | 真实权益交付及订单管理 |
| 服务记录 | SQLite保存模拟服务记录 | 正式服务记录与执行回执 |
| 反馈回传 | 后端保存并在页面展示 | 结构化提供给 A 汇总，用于阶段4评价，并供 B 在权限范围内读取 |

### C11 数据与权限

1. 患者画像由阶段2提供，阶段3不重新计算。
2. 页面中的模拟患者信息必须明确标注为模拟数据。
3. 积分余额和兑换记录应由程序管理，不允许大模型随意修改。
4. 服务申请必须经过患者确认。
5. 涉及第三方的信息共享必须经过相应授权。
6. 服务状态必须有实际操作或服务方反馈作为依据。
7. 不得将AI生成的建议误认为真实服务已经执行。
8. 真实医疗风险需要按照医疗安全流程转介。
9. 不得把智能药盒开盖记录直接等同于患者已经完成服药。
10. 当前没有接入真实数据或服务的功能，应明确显示为演示功能，不得伪装成已经实现。

### 8.2 网页基本要求

移动端优先，同时支持 Windows 桌面浏览器。视觉清楚、克制；避免后台式布局、过多卡片及冗余文字。按钮有真实可见反馈，不以静态图代替业务。显示患者/案例和模拟来源，患者切换时清除旧卡片与待响应控件。

### 8.3 A 全链路联调

请将 A 的各模块连接成可验证的 Python 后端闭环，与网页、B 及其他成员约定的接口联调，并整理便于他人运行的交付材料。

#### 完成目标

跑通：

录入资料 → 核对正式计划 → 提交手动或模拟记录 → A4 清洗 → A6 统计 → A5 摘要 → 接收 B 的支持或执行请求 → 查询执行结果与反馈。

本任务是联调已有能力，不重新开发整个平台。B 和其他成员未接入时使用明确标记的模拟适配，真实及模拟接入分别列出。

#### 输入与准备

- 总约束、公共契约和各模块实际代码、数据库与配置。
- 其他成员当前接口及网页接入方式。
- 两名虚构患者、固定用药计划、记录和设备场景。
- 明确隔离的测试环境，以及真实和模拟依赖清单。

先核对共同字段、状态、单位、时间和操作维护方。接口冲突通过统一约定及适配解决，不各自保留一套相同含义的数据或修改别人的核心逻辑。

#### 固定演示与验收流程

**1 资料与计划**

为患者甲上传虚构病历并人工录入草稿，通过真实或标记为模拟的确认流程取得正式计划引用。待确认草稿不进入正式统计。

患者乙用于验证数据隔离。切换管理对象不改变记录原有患者归属，家属只在授权范围内操作。

**2 用药记录**

初始化 7 天、14 个已到时的有效计划时段；准备 10 个本人确认已服、2 个仅开盒、2 个无记录，本人未服和暂时延迟均为 0。

通过手动接收和设备模拟入口取得相应证据，不直接写死统计返回值。重复发送已有的一条开盒事件，统计应保持 10/14。

再为一个未知时段补传有效本人确认已服，统计变为 11 个本人已服、2 个仅其他证据、1 个未知，本人未服和暂时延迟均为 0，比例为 11/14。记录、摘要及更新时间应对应更新。

**3 指标与质量**

提交一个有效指标、一条缺失采集状态和一个未知单位样例。有效值进入相应趋势，缺失显示不足，未知单位按 A4 规则处理，不被猜测为正常值。

摘要引用真实计算结果，不另算一套确认比例，也不因缺少生理数据删除有效用药统计。

**4 B 与社会支持交接**

让 B 或模拟适配读取摘要，并提交一个模拟执行请求。A 保存任务和结果，展示及患者响应仍由 B 对接，不能因为 A 已执行就默认患者已响应。

社会支持反馈按其既定维度读取；只有服务申请时不显示为服务完成。真实外部服务未接入的地方明确标记。

**5 失败与权限**

验证重复提交、患者越权、家属授权撤销、错误单位、计划或存储依赖失败，以及取消或过期任务。失败不能返回虚假成功，也不能清空他人的测试或实际数据。

#### 网页联调

网页通过接口展示记录、统计、摘要及执行结果，完成刷新、重试、患者切换和错误提示验证。前端已有页面优先复用，不另起一套独立产品导航。

A 负责向上述页面提供记录、统计、摘要和执行接口，不因此重复开发一套前端。首页概况和“我的”中的用药记录报告复用 A 的同一统计来源。

如果网页尚未接入，先用接口调用完成后端联调，交付前端所需数据示例，并明确标记网页联调未完成；不能把接口测试通过写成网页已可交互。

如网页原型仍使用本地模拟数据，应明确哪些页面已经换成真实后端接口，避免表面可点击而后台数据未变化。

#### 交付材料

整理一份简明 README，包含：

1. 本期实现功能和模块维护方。
2. 实际依赖、配置、数据库初始化或升级、启动方法。
3. 接口列表、调用样例及供 B 和网页使用的字段说明。
4. 虚构数据初始化、演示顺序和预期结果。
5. 已执行测试、实际结果、失败或未完成项。
6. 模拟依赖清单及真实服务替换位置。

测试重置只能针对明确隔离的数据范围，不默认清空现有库。配置示例不包含真实密钥，交付中不夹带真实患者病历。

#### 最终通过条件

- 数据确实经过接收、保存、处理和计算，查询结果与实际记录一致。
- 重复请求不重复计数，补录后记录、统计与摘要一致更新。
- 关键权限和失败场景有真实验证结果。
- B 与网页的真实接入范围清楚，没有假装完成的外部服务。
- 其他成员按说明能够启动和调用，尚未确定的接口细节或依赖未接入的部分明确列出。

请交付联调修复、实际测试结果、简明运行说明和交接清单。只有完成相应代码并验证后才报告功能完成；本组 Prompt 写齐本身不代表平台已经建成。

### 8.4 B 对话评测与展示

“支持服务”的“AI 情感支持”页面展示聊天、邀请、建议和实际模式，并复用核心用药确认入口；辅助区可折叠，展示来源、原话、线索、知识引用、策略、版本及操作结果，不显示思维链或未经验证评分。

演示控件放入独立的“演示控制台”，与患者日常导航和交互分开，提供案例、会话、历史、模式/流水线配置、事件及故障模拟。患者不能通过消息改变供应商、模型地址或系统规则。显示当前实际 `mode` 和 `actual_pipeline`。

第一版非流式；如果后续加入流式，辅助分析及可执行建议只能在完成校验后发布，不能先执行后校验。网页安全渲染文本，不执行模型返回 HTML。

建立固定中文评测案例，覆盖倾听、快速求助、倦怠、顾虑、拒绝、话题转换、未知背景、冲突资料及紧迫危险。评价共情具体性、自主支持、提问负担、事实依据和边界，不能只评价用户是否表示顺从。

比较 `single_pass/star` 或不同模型时固定案例、提示词/知识版本及配置，记录响应时间、调用次数、用量和人工评价。LLM 自评或模拟用户结果不能单独解释成真实患者效果。真实付费评测只在用户明确要求后执行。

请按照以下清单生成网页原型，并确保每项均可以实际操作。

#### 首页

- 展示模拟患者当前画像。
- 可以切换不同患者画像，模拟阶段2输出。
- 切换画像后，首页推荐卡片同步变化。
- 展示今日用药记录进度（模拟数据）。
- 展示积分余额快捷入口。
- 展示最近一条服务状态。
- 点击支持卡片能够进入社会支持页面。

#### 支持服务中的社会支持页面

至少提供以下三种典型情境：

**场景A：操作与外部条件受限型**

- 展示药品补充提醒。
- 展示家人取药协助入口。
- 展示医院药师咨询入口。
- 提交申请前进行必要授权确认。

**场景B：社会情境与生活冲突型**

- 展示匿名同辈支持微小组。
- 展示同病种、同用药阶段、相似作息等匹配标签。
- 提供申请加入和暂不参与选项。
- 展示志愿者情感陪伴入口。

**场景C：用药顾虑与心理抗拒型**

- 展示医院药师专业咨询入口。
- 提供咨询申请及授权确认。
- 展示必要的家庭情感支持入口。

#### 积分权益页面

- 展示当前积分余额。
- 展示积分获取规则。
- 展示可兑换服务及对应积分。
- 积分充足时允许兑换。
- 积分不足时禁用兑换按钮并明确提示。
- 兑换成功后正确扣除积分。
- 自动生成兑换记录。
- 展示历史兑换项目、积分消耗和交付状态。

#### 我的页面

- 展示个人信息及授权管理入口。
- 设置独立的服务记录入口。
- 展示服务名称、服务主体、申请时间和状态。
- 支持按全部、已申请、进行中、已完成、已取消和未能完成筛选正式服务记录；待确认草稿单独呈现，不混入已提交服务列表。
- 允许在演示模式中按约定流转模拟服务受理、执行、完成、取消和未能完成，禁止使用模拟按钮任意改写终态。
- 服务状态改变后，首页最近服务状态同步更新。
- 不将积分兑换记录混入社会支持服务记录。

#### 服务记录状态流转

服务记录必须遵守以下状态生命周期：

**已申请 → 进行中 → 已完成。**

并支持：

- 已申请或进行中 → 已取消；
- 已申请或进行中 → 未能完成。

已完成、已取消、未能完成作为终态，不通过演示按钮随意改回处理中；需要再次申请时创建新的申请。

服务完成不等于干预有效。服务执行结果和患者反馈分别记录，用于后续评价。

实际服务中，状态应由服务方或可靠业务接口回传。当前原型可以通过模拟按钮演示合法状态变化，但必须清楚标注为模拟操作。

验收时至少验证：未确认或未授权的草稿不创建实际服务申请、不通知服务方；完成确认后只创建一条正式记录；合法流转能够查询；非法流转和终态回退被拒绝；取消与失败分别保留；服务完成后可以独立收集患者评价。

#### 反馈机制演示

服务完成后，提供简短的反馈入口，至少能够收集：

- 支持需求是否得到缓解；
- 患者是否愿意继续接受该类支持；
- 患者对本次服务的主观评价。

将反馈整理为三个既定维度：

1. 支持需求变化（Support Needs）；
2. 支持接受程度（Support Acceptance）；
3. 干预效果（Intervention Effectiveness）。

在原型中展示模拟的反馈回传结果。

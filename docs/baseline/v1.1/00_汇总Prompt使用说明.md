# 全平台汇总 Prompt 使用说明

适用文件：同目录的《00_全平台分阶段编码汇总Prompt.md》，执行基线 v1.1。本版增加指定 GitHub 仓库及阶段同步要求；v1.0 已保留归档。

## 1 这两份文件各做什么

汇总 Prompt 是交给编程 AI 的执行需求，包含总约束、统一契约基线、O/A/B/C 业务、S00 至 S07、工作记录和最终交付要求。

本说明供使用者组织工作、审阅阶段产物和接续开发。四份原始 Prompt 保留作来源，不再分别投喂以要求各自创建工程，也不再使用原稿各自的“阶段1/2/3”编号执行。

本次交付是 Prompt 和使用说明，尚未编写应用代码、调用真实模型或运行应用测试。编程 AI 后续生成的代码必须按各阶段实际验证。

## 2 开始前准备

1. 在拟用于开发的 Windows 环境打开统一工作目录；有已有代码时保留其目录和数据，不另起同义工程。
2. 将汇总 Prompt 提供给同一个编程 AI，允许其读取实际工作区。文件内容较长，优先让 AI 直接读取文件。
3. 提供已有工程或说明尚未编码。模型供应商暂未选定并不阻断阶段规划，默认模拟模式。
4. 不在聊天中粘贴密钥。需要真实 API 时，在本地按配置说明填写真实配置，保持其不入版本控制。
5. 早期只用虚构案例和隔离测试数据。真实外部服务未接入时，演示标记必须保留。
6. 目标仓库为 https://github.com/kevinlee134679-web/dachaung，开发分支使用 `develop`。建议工程目录为 `D:/大学/大创/dachaung`，由 S00 检查后确定；已有克隆优先复用，不把整个研究工作区初始化为应用仓库。
7. 在实际执行编码的电脑上准备 Git 和 GitHub 登录。仓库可公开查看不等于具有推送权限，S00 记录检查结果；不在聊天中提供令牌或私钥。

本次只更新 Prompt 文档，尚未克隆、创建分支或上传到 GitHub；这些准备由后续执行 S00 的编程 AI 在实际开发环境完成。

## 3 第一次只执行 S00

将下面的指令与汇总 Prompt 一起发送：

```text
请完整读取《00_全平台分阶段编码汇总Prompt.md》。
现在只执行 S00，不编写应用业务代码，不调用付费 API。
先检查实际工作区，输出本期范围、全平台接口目录、公共对象草案、
数据与模块维护方，以及具体待确认事项。
同时核对 GitHub 仓库 https://github.com/kevinlee134679-web/dachaung、
实际工程目录、develop 分支及登录和访问情况，报告准备结果。

沿用已确认规则。第一轮只详细展开公共基础与 O 的字段和接口卡，
等待我确认后，再依次展开 A、B、C 和全流程契约。
明确区分已确认、建议和待确认，不自行冻结新业务取舍。
如创建规划文档或工作记录，遵守追加式历史规则。
已确认的规划文档可按总约束提交并推送至 develop，核验远程结果；
无法推送时如实记录，不开始应用业务编码。
```

S00 可以分多轮完成。你需要检查：

- 每个页面操作是否有接口，是否存在重复入口或职责缺失。
- 同一患者、计划、时段、会话及服务记录的 ID 是否能贯通。
- 字段是否写全类型、必填、可空、默认值、枚举、单位和来源。
- 状态和幂等是否明确，失败有没有被伪装为成功或空数据。
- 五类统计、授权、服务创建、积分和真实/模拟边界是否沿用已确认规则。
- 所有本期需要的对象与接口是否已经确认；后续扩展和未解决事项是否单列。
- 仓库、实际目录、分支及同步状态是否清楚；是否把公开可读误写为已验证可推送。

确认一批时可以发送：

```text
确认本批所列契约。请记录确认范围和版本，继续 S00 的下一批。
不要开始业务编码。
```

完成所有必要确认后，要求输出冻结的契约版本、确认记录和待定清单。不要仅凭示例 JSON 或一张接口目录就认为完整契约已经确认。

## 4 分阶段编码顺序

| 阶段 | 主要工作 | 你审阅的关键结果 |
| --- | --- | --- |
| S01 | 公共工程、数据库基础、统一网页外壳、追加式记录 | 能启动，初始化/迁移可执行，首个编码阶段工作记录完整 |
| S02 | 身份、家庭授权、八题问卷、画像与计划、资料录入 | 可从身份进入计划；未验证预测如实说明 |
| S03 | A 的数据接收清洗、模拟设备、匹配统计、摘要、公共执行及提醒接入 | 重复不计数，补录更新，10/14 和 11/14 一致 |
| S04 | B 的单次模型调用、知识基础、对话、线索、邀请和模式 | 共情对话、用户接受后极简、恢复、历史与来源一致 |
| S05 | C 的社会支持、服务状态、积分、兑换及反馈 | 唯一申请、合法流转、兑换扣减与流水、反馈回传 |
| S06 | STAR、知识版本、规则与调度、回调和异常集成 | 分步有预算，重启/重复/撤销/失败等可验证 |
| S07 | 全站、回归、干净环境复现及完整交付 | 所有清单项目齐全，实际可运行，限制如实列出 |

S04 是先看到情感支持闭环的里程碑。只做到 S04 时仍有后续工作，不应声称完成了整份扩展汇总 Prompt。若项目决定提前止于演示，明确登记删减范围和未完成项。

执行某阶段时发送：

```text
请执行 S01（后续替换为当前阶段编号）。
开始前读取汇总 Prompt、有效契约、docs/工作记录.md 和当前代码，
核对前置条件，只实现本阶段范围。

完成适当验证后，在 docs/工作记录.md 追加本次结果，保留全部历史。
必须包含完成情况、未完成情况、验证证据、下阶段要求及总体约束快照。
按总约束提交本阶段允许上传的成果，推送到指定仓库的 develop 分支，
核验远程已包含本次提交；排除密钥、运行数据库及无关资料。
报告记录 ID、实际文件、验证结果、分支、提交哈希、同步状态和待处理事项，
然后等待下一阶段指令。同步失败时保留本地工作并如实记录。
```

同一阶段没有完成时，发送“继续当前阶段”，要求沿用已有代码并补齐未完成项；修复和补充也新增记录，不覆盖上次条目。

阶段较大时，可要求“先列出本阶段子任务，本次只完成第一批并验证、追加记录”。之后按工作记录继续下一批；阶段内分批不改变 S00 至 S07 的总体顺序。

## 5 工作记录如何使用

统一文件为 `docs/工作记录.md`。这是开发状态的长期依据，不是每轮替换的最新摘要。

- 至少从 S01 起，每阶段结束都有记录；S00 确认、中断及修复也记入历史。
- 记录 ID 递增，如 R0001、R0002；编码阶段可以相同，因为一个阶段可能有多次尝试。
- 每条记录必须包含你要求的四项：本阶段代码完成情况、未完成情况、下阶段代码要求、代码编写总体约束；另有实际验证、版本和代码基线。
- “未完成”“未验证”“模拟”是有效状态，不能为了好看填成完成。
- 历史结论错误时，追加更正条目引用旧 ID，禁止删除旧记录或回写旧时间。
- 记录器追加前后校验历史前缀及 SHA256，不允许历史被覆盖。测试只在隔离临时文件上进行。
- 下阶段首先读取全部记录，结合当前代码核实。记录不能代替代码存在和实际运行证据。
- 工作记录填写本次工作的起始提交和已知同步状态；本轮新提交哈希及远程核验结果在阶段报告中给出，后续记录带入。不为回填当前提交而修改旧记录。
- 每阶段审阅时，在 GitHub 的 `develop` 分支核对阶段报告列出的提交已存在，相关源码、测试、文档和工作记录已同步。推送失败与功能未完成分别登记。

用户中途停止或环境无法继续时，要求：

```text
请停止当前阶段的新增实现，保存已经完成的工作，
追加一条中断交接记录，明确完成、未完成、失败、代码基线、
恢复步骤、下阶段要求和有效总体约束。不要覆盖任何旧记录。
```

## 6 更换聊天或编程 AI 后如何接续

提供：汇总 Prompt、当前工程、完整工作记录、冻结契约、版本登记及必要结果文件。使用说明可同时提供，但不能只给聊天中的一句进度。

接续指令：

```text
请先读取汇总 Prompt、docs/工作记录.md、有效契约、版本登记和当前代码。
不要重新生成整个工程，也不要覆盖工作记录。
核对最后有效记录与代码是否一致，列出差异、当前阶段和未完成项。
核对目标仓库、develop 分支及本地和远程差异，保留既有未提交工作。
我本次授权你继续 Sxx；只执行该阶段范围。
若发现需要改变已确认业务或契约，先给出修改内容和影响供我确认。
结束后追加新记录，并验证历史前缀未改变。
随后提交并推送本次允许上传的成果，报告提交及远程核验结果。
```

如果 AI 无法直接读取文件，将总约束、当前阶段、相关模块、有效契约及工作记录一起提供。不得省略总体约束，也不能用“规则同前”替代已丢失的上下文。

## 7 如何确认最终交付

最终要求 AI 对照 Prompt 第 9 章逐项提交路径、版本和验证状态，包括：

1. 可运行源码、依赖清单及配置示例。
2. 数据库初始化、迁移脚本及实际升级验证。
3. 数据字典、接口与状态说明。
4. 模拟数据、验收用例、测试代码及真实测试结果。
5. 任务调度说明、Windows 启动与运行说明、演示脚本。
6. 规则、评估、知识、数据结构、契约、提示词、模型配置及数据/测试版本。
7. 完整追加式工作记录、最终交付清单、已知限制与外部依赖状态。
8. GitHub 仓库地址、实际交付分支、完整提交哈希及从该提交获取工程的复现结果。

可发送：

```text
请执行 S07 最终交付验收。按汇总 Prompt 第 9 章逐项核对，
列出实际路径、版本、验证命令与结果、模拟/真实/未接入状态。
从目标 GitHub 仓库的交付提交获取工程，
在新的隔离环境验证从安装、初始化或迁移到启动和演示的流程。
不能通过未实现功能、静态假数据或未执行测试来凑齐完成清单。
最后追加工作记录；如有必要验收失败，如实列出，不标记全项目完成。
提交并推送允许上传的交付材料，核验远程包含本次提交，
报告仓库、交付分支、完整提交哈希及同步状态。
```

文档齐全不等于业务已完成；接口测试通过不等于网页联调完成；模拟投递不等于真实服务送达；记录趋势不等于临床效果。最终以实际代码、数据、页面和验证证据共同判断。

## 8 格式与使用约定

汇总 Prompt 使用一个一级标题，顶层章节为二级标题，模块为三级标题，模块内部为四级标题；更细步骤使用加粗标签。列表、表格、JSON 和路径表达统一。

公共技术、导航、响应和历史记录要求已集中放在前部，模块中的重复说明已整理；来源文件旧的局部阶段编号不再作为执行入口。

后续修订 Prompt 或契约时新增版本说明，保留原版本和历史工作记录。涉及已确认业务的实质变更，继续先审阅、确认，再修改。

GitHub 提交与工作记录共同保留开发过程；阶段自动同步针对 `develop`，合并主分支或发布版本按用户明确指令执行。

# S05 第一批运行与交接

应用 0.5.0，schema 0008。适用契约为 C-v0.2、继承的 C01–C03 字段和接口卡、public-o-v0.5 及其 O 授权增量。当前运行范围为本地虚构资源目录和候选匹配。

## 在独立虚构库运行

从仓库根目录执行。命令新建独立目录，并使用本机空闲端口。要验证升级，可把来源明确的 schema0007 虚构库复制到该目录，再针对副本执行 `migrate` 代替 `init-db`。

```powershell
$demoOutput = Join-Path (Get-Location).Path ('test-output/s05-catalog-' + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $demoOutput | Out-Null
$env:DATABASE_PATH = Join-Path $demoOutput 'catalog.sqlite3'
$env:APP_ENV = 'test'
$env:AUTH_MODE = 'demo'
$env:LLM_MODE = 'mock'
$env:DIALOGUE_PIPELINE = 'single_pass'
$env:HOST = '127.0.0.1'
$env:PORT = '8018'
& ./.venv/Scripts/python.exe -B -X utf8 -m medplatform init-db
& ./.venv/Scripts/python.exe -B -X utf8 -m medplatform seed-demo
& ./.venv/Scripts/python.exe -B -X utf8 -m medplatform seed-support-catalog
& ./.venv/Scripts/python.exe -B -X utf8 -m medplatform serve
```

启动前确认端口空闲。首次在空目录登记会写入 7 个版本，当前展示 5 个资源。重复登记同一份清单返回 `versions_added=0`。目录缺少种子时，C02 和依赖目录的 C01 请求返回 503。初始化、迁移和登记均由显式命令执行。

## 网页和权限

1. 选择「演示患者甲」，点击「管理自己的用药」。如副本没有画像，在「我的 → 八题问卷」提交一份虚构回答，再在「画像结果」按既有 O 流程生成描述性结果。
2. 从首页进入「查找社会支持」，或从「支持服务 → 社会支持」进入。可查看 O 的已登记画像和可用资源。
3. 选择药学咨询并点击「查看匹配」。候选可查看确切资源版本、虚构主体、资质状态和可能涉及的共享类别。选择情感陪伴可查看两项同级候选。
4. 保留「使用已有明确需求」并点击「查看匹配」，若当前没有已确认的分类需求，页面说明信息不足。选择「暂不需要支持」会返回 `none`。
5. 家属须先选择获准的患者。患者在「我的 → 家庭授权」明确授予 `support:read` 才能查看该对象的目录和候选。另授 `profile:read` 才允许使用画像，授撤分别生效。

页面中的资源、主体、资质和供给均为虚构；查看候选与详情是只读操作。页面显示的共享类别为资源配置，未在浏览时共享任何资料。

## 接口与版本

| 卡 | 当前行为 |
| --- | --- |
| C01 `GET /api/v1/patients/{p}/support-recommendations` | 可按原枚举传 `need`，以当前明确查询需求匹配，临时使用允许读取的 O 画像。资料不明、未采集、权限受限、已知不符合和无候选分别反馈。 |
| C02 `GET /api/v1/support-resources` | 在当前授权对象下列出可用的模拟资源，默认 `channel=support`，用 `cursor/limit` 分页。当前 rewards 目录为空。 |
| C03 `GET /api/v1/support-resources/{id}` | 返回当前可用版本，缺失或停用资源返回 404。 |
| C40 本批读取与关联 | 复用 O20及其精确的患者和 `profile:read` 检查。既有 O 写入流程负责登记。 |

`data/demo/support_resources.json` 登记内部来源、审核状态、前序版本和适用条件。更新目录时在清单末尾追加具有同一资源 ID、新版本和明确前序的条目，再显式执行登记命令。并发登记由统一事务串行化，同版本同内容幂等，同版本异内容或前序冲突会回滚。资质和审核状态分别保存，虚构药师没有核验资质。历史资源在 `c_support_resource_versions`，当前版本由 `c_support_resources` 引用。

例如 C01 对药学咨询返回 `source_refs` 中的 `C/support_resource/resource-pharmacist-demo/resource-demo-v2`。使用画像时同时返回 O 的 `profile_id` 和修订。查询结果是实时投影，取证时可保留返回结果，凭引用定位不可变资源版本和 O 历史画像。C03 仅按原契约读取当前版本。

适用条件仅对明确依赖已有 O 类型的资源生效，未知类型无法满足该条件。无该项条件的候选可以按明确需求返回。恰有一项时可使用契约的主项字段，两项同级时同时显示为候选。超过可用同级栏位时保留所有合格版本引用，等待明确排序规则。

本批沿用既有 O 描述性画像，CAS 保持空值。C40 受控切换写入口、A/B 自发需求来源、正式服务和反馈路径待后续明确范围。运行日志及隔离数据库只保存于本机。


## S05 第二批服务草稿与本人确认

应用 0.5.1，schema 0009。C04–C06 和 C34–C36 使用 C-v0.2、public-o-v0.5、flow-v0.1 及继承契约。

### 隔离启动

沿用前文的独立目录、`DATABASE_PATH` 和本地空闲端口。0008 副本执行 `migrate`，新空库执行 `init-db`。首次空库完成虚构账号和目录登记后，显式登记 O 演示接收主体，再启动。

```powershell
& ./.venv/Scripts/python.exe -B -X utf8 -m medplatform seed-demo
& ./.venv/Scripts/python.exe -B -X utf8 -m medplatform seed-support-catalog
& ./.venv/Scripts/python.exe -B -X utf8 -m medplatform seed-support-recipients
& ./.venv/Scripts/python.exe -B -X utf8 -m medplatform serve
```

O 有 5 条独立的受控模拟接收主体登记，来源是 `data/demo/o_support_recipients.json`。登记逐项比对精确目录版本、主体 ID、主体类型及服务用途，完整重放新增 0 条。只有 C 目录条目时，允许准备草稿，C34 拒绝缺 O 登记的确认。依据原 C34 的直接本人确认示例，已登记的非家庭模拟主体没有通用家庭 Grant 依赖，`related_grant_ids=[]`。已存在确切 O Grant 依赖的有效性由 O 以原 ID、版本、关系状态和截止时间重新核验。

### 网页操作

1. 在「我的 → 家庭授权」为虚构家属配置「社会支持目录和候选（只读）」及「协助准备服务草稿」。家属选择获准患者。
2. 从「支持服务 → 社会支持」选择资源，点「查看资源详情 → 准备服务问题」，填写并保存。记录草稿编号。家属可读取、修改草稿。
3. 患者本人进入同一页，输入草稿编号。核对正文和精确资源版本，查看接收主体、用途、必要类别，再选择可选类别，明确勾选核对后确认。
4. 在「我的 → 服务授权」查看当前或历史状态，填写理由并明确勾选撤销。浏览器只记住业务编号和提交指纹，实际状态经接口重读。历史面板支持本浏览器已核对或用户提供的确认编号。
5. 刷新恢复已保存草稿和确认。冲突时读取最新修订并保留当前编辑器中的文字。未知结果先按原请求重试，或按已知业务编号核查。重新载入页面后的未保存正文需要从原输入恢复。

### 接口与持久化

| 卡 | 方法和路径 | 关键行为 |
| --- | --- | --- |
| C04 | `POST /api/v1/patients/{p}/service-drafts` | 手工需求绑定当前可访问版本，201。 |
| C05 | `GET /api/v1/service-drafts/{id}` | 200，按当前授权读取草稿与有效关联。 |
| C06 | `PUT /api/v1/service-drafts/{id}` | 200，以 `meta.revision` 保护编辑，追加内容修订。 |
| C34 | `POST /api/v1/patients/{p}/service-confirmations` | 本人锁定精确 `draft_revision`。新建 201，同范围有效复用 200。 |
| C35 | `GET /api/v1/service-confirmations/{id}` | 本人读取 200，按 C 与 O 当前状态投影。 |
| C36 | `POST /api/v1/service-confirmations/{id}/revoke` | 本人提交期望修订和理由，200，保留撤销历史。 |

首次确认时 C、O 使用同一 UTC 时点，各自默认 24 小时，右端点失效。复用保留原确认和 O 范围 ID、原截止时间。正文变更后须明确核对新修订。范围变更先撤销旧确认。撤销后保留历史，关联草稿仍是 `preparing`。先校验当前权利，再读取或重放回执。O 共享范围、C 确认、精确草稿关联和回执由同一 SQLite 事务提交。O 范围撤销及 C 撤销审计同样原子提交。

第一批目录和匹配规则沿用。家庭接收方、B 建议和 B23 正式接入、C07 正式服务及 A 任务仍留在既定后续范围。两批验收索引见 [verification.json](verification.json)，第一批原字节归档见 [verification.batch1.json](verification.batch1.json)。


## S05 第三批正式服务与模拟派发

应用 0.5.2，schema 0010。前两批的目录、草稿、O 共享范围和原运行证据保留。第三批接口接入范围以本节为准。

### 隔离启动与验收

沿用独立的 `DATABASE_PATH`、空闲端口、`127.0.0.1`、`demo/mock/single_pass`。用 0009 文件的副本运行 `python -m medplatform migrate`。新空库运行 `init-db`，再依次显式运行 `seed-demo`、`seed-support-catalog`、`seed-support-recipients` 和 `serve`。已初始化的副本可先用 `db-status` 核对 0010。

1. 虚构患者在「支持服务 → 社会支持」选择资源、保存草稿、本人确认共享范围。确认后再勾选「我明确按本草稿申请模拟服务」并点击「提交正式服务」。
2. 在「我的 → 服务记录」查看服务编号、正式状态和派发任务编号。提交超时先从原草稿读服务编号，或在服务记录核实。待处理网页需要显式刷新。没有找回结果时，用原请求条件重试。
3. 退出患者会话，登录虚构管理员，打开「我的 → 社会支持演示控制台」，填写原任务编号后执行一次模拟派发。A36 保存 `delivery_status=submitted` 时，C 仍为 `submitted`。重复原键返回原尝试，结果不明时核对原任务及其执行记录。也可按既有 `run-task` 命令执行受控原任务。
4. 管理端填写服务编号和当前服务修订，选择模拟处理中并填写原因，再用当前修订单独登记模拟完成。只有合法状态变化才入库。患者回到服务记录并刷新，核对状态、时间和结果。家属需有 `services:read`，正文及答复按最小权限隐藏。派发详情还需 `tasks:read`。
5. C11 默认关闭独立模拟回执入口。仅在本地隔离测试中，可为单一已登记模拟主体设置 `DEMO_SERVICE_RECEIPT_SUBJECT`，并通过独立、至少 32 字符的 `DEMO_SERVICE_RECEIPT_TOKEN` 及请求头 `Authorization: Bearer …` 提交回执。测试凭据使用临时环境配置。普通会话无法获得此主体身份，真实接收适配仍未启用。

### 接口和数据

| 卡 | 入口 | 核验与结果 |
| --- | --- | --- |
| C07 | `POST /api/v1/patients/{p}/services` | 本人，精确草稿修订及当前 C/O 确认。201 返回唯一 Service。 |
| C08 | `GET /api/v1/patients/{p}/services` | 当前个案和读取权限，支持五状态筛选及 cursor。 |
| C09/C10 | `GET /api/v1/services/{id}`、`POST /api/v1/services/{id}/cancel` | 读取权威状态。本人以当前修订取消活动服务。 |
| C11 | `POST /api/v1/integrations/service-receipts` | 独立模拟身份、稳定来源号、当前修订、时序及授权。返回最小回执。 |
| C12 | `POST /api/v1/demo/services/{id}/transitions` | 演示管理员调用合法状态机，启动及完成要求可核模拟派发。 |
| B23/B24 | `POST /api/v1/referrals`、`GET /api/v1/referrals/{id}` | B23 唯一创建委派至 C07 的领域服务。B24 从 C 读当前事实。 |
| A36 | `POST /api/v1/tasks/{id}/run` | 注册 C 的 `dispatch_service`，只执行 C 创建的精确任务。显式执行。 |

0010 增加正式服务、追加式状态历史、唯一派发事实以及按主体/来源号去重的回执表，并给 C 草稿增加状态和正式服务引用。正式服务与关联、任务、审计、变更通知原子提交。取消、撤权与派发提交按同一 SQLite 写事务裁决，过期截止取有效确认、O 范围及必要 Grant 的最早期限。未知原执行可由可信模拟回执确认，其既有未知记录保留。五状态和合法迁移遵循 C11，A 的派发成功与 C 模拟完成独立记录。

第二批精确复核、历史版本和第三批证据见 [verification.json](verification.json)。第二批提交时的验证摘要按原字节保存在 [verification.batch2.json](verification.batch2.json)。
